## Profile 存储容量评估

2026-11-06 19:07（北京时间）通过项目 SSH 别名在云主机采样，Profile 开发与验收选择复用现有 MongoDB、Redis。

| 项目 | 实测 |
| --- | --- |
| CPU | 2 vCPU，1 / 5 / 15 分钟负载为 0.25 / 0.15 / 0.12 |
| 内存 | 总计 3495 MiB，MemAvailable 2001 MiB，swap 为 0 |
| 磁盘 | 根盘 40 GiB，可用约 18 GiB，Docker 数据与备份位于同一文件系统 |
| 容器 | 7 个在线，内存上限合计 2528 MiB。MongoDB 使用约 177 MiB / 上限 640 MiB，Redis 使用约 20 MiB / 上限 160 MiB |

独立实例按现有数据库规格估算需要额外 800 MiB 容器预算。合计上限 3328 MiB，峰值时仅余 167 MiB 给宿主系统和其他进程。该机器有启动第二套服务的瞬时余量，但在无 swap 的开发机上，内存预算不足以同时覆盖这组上限和系统开销。该判断基于配置预算与开发负载快照，生产容量仍需按实际实体数、摘要大小和访问峰值测量。

测试库使用 `tgame_test.entity_profiles` 集合，Redis 使用 `tgame:test:profile:<EntityId>`。这是逻辑命名隔离，权限沿用原有测试账号。MongoDB 保存权威摘要，Redis 缓存 TTL 为 60 秒。成功写入或撤回后失效对应缓存；若 Redis 暂时不可用，Profile 读取 MongoDB，失效失败的旧缓存最多保留到 TTL 到期。存储地址见 [storage.test.yaml](../code/server/config/storage.test.yaml)，独立实例迁移时可单独修改 Profile 的地址。
