目录骨架已于 2026-11-05 创建，现有脚本、协作规范和仓库内的 crane 工具已迁移，Git 忽略规则已应用；尚未创建游戏源码工程或安装新的工具。后续细微调整默认只向用户展示 diff；用户要求完整结构时再展示全貌。

## 组织原则

- 先采用单 Git 仓库，游戏源码集中到 `code/`，作为 Codex 日常打开的目录。
- 客户端与服务器目录保持对称；两端的运行配置、生成代码和导出数据分别使用 `config/`、`generated/`、`data/`。
- 自研工具、第三方工具和脚本统一放在顶层 `tools/`，按工具名称组织，不再增加 `third-party/` 分类层。
- 策划维护的原始文件统一放在顶层 `design/`；大型资源、工具实体、框架源码和 SDK 不纳入游戏源码的日常工作范围。
- 开发工具、维护策划文件或排查生成问题时，按任务需要访问相应目录。代码项目、构建配置、依赖声明和测试应保持可用。

## 代码职责与依赖边界

`client/app/` 是客户端应用入口，当前采用 Blazor WebAssembly。未来客户端引擎可能更换为 Godot、Cocos 或其他方案，尚未选定，不提前建立对应适配工程。

`server/app/` 是服务器启动入口，负责读取配置、启动引擎、加载业务逻辑和处理退出；它承担之前草案中 `host` 的职责。`server/engine/` 放可复用的服务器基础能力，不依赖 TGame 的业务实现或专属共享定义。`server/model/` 放常驻业务数据结构，`server/logic/` 放可热重载的业务逻辑。

进程按类型承载 Entity。八种进程的 SinglePoint 类分别放在 `logic/entities/` 下各自的目录中，例如 `baseServerSinglePoint/BaseServerSinglePoint.cs`。类声明上的 `SinglePointFor` 标注是进程类型到类的唯一映射来源。宿主扫描、校验后创建当前类型的实例，发现服务地址后调用其初始化方法。常驻身份数据位于 `model/entities/SinglePointState.cs`，连接的生命周期及就绪状态由宿主管理。联通工程目前将 model 和 logic 源码一起编译。

划分其他 Entity 时，model 保存业务逻辑更新后仍需保留的内存状态。例如 Body 的公会 ID、Soul 的当前生命值属于 model，修改公会归属、计算伤害的方法属于 logic。是否写入 MongoDB 由各字段的存盘需求决定。

`shared/` 放两端实际需要共享的协议、代码和数据。当前两端可引用同一个共享 C# 项目，不复制维护。共享代码不依赖客户端引擎专用 API 或服务端存储实现。未来客户端更换语言时，以协议源定义为基础生成对应代码，不预设 C# 源码仍能直接复用。

目录划分不直接等同于程序集划分；具体 C# 项目数量、引用关系及热重载加载边界在实现时确定。

## 配置与生成流程

| 内容 | 维护位置 | 使用或生成位置 |
| --- | --- | --- |
| 客户端运行配置 | `code/client/config/` | 由客户端按需加载或打包，只含可公开的数据 |
| 服务器运行配置 | `code/server/config/` | 按开发、测试、生产环境维护 YAML |
| 策划 Excel 原表 | `design/tables/` | 导表工具按使用范围生成到 `code/client/generated/`、`code/server/generated/` 或 `code/shared/generated/` |
| 行为树、技能等编辑器源文件 | `design/editors/` | 按编辑器原生导出格式，输出到对应端或共享目录下的 `data/` |
| 协议源定义 | `code/shared/protocols/` | 协议工具生成到对应使用方的 `generated/` |
| 手写运营开关与参数 | `code/server/logic/` 中的配置代码 | 延续集中维护 C# 配置的约定，运行中需调整的值不使用 `const` |
| 工具配置、导出规则和模板 | 对应 `tools/<工具名>/` | 随工具维护，不设公共 `config/tools/` |

`generated/` 专门存放自动生成的代码，包括协议消息类和表格导出的 C# 配置代码；`data/` 存放程序读取的导出数据文件。修改源定义后重新生成，不手工维护生成代码。每类配置和协议应明确使用方，只有双端需要的内容进入 `shared/`。

## 工具与运行产物

每个自研工具在自己的目录内维护源码、测试和必要配置；第三方工具同样按名称放入 `tools/`，将项目所需的可执行程序、配套依赖和上游说明、许可证一并纳入版本管理。仓库提交固定实际工具版本，不另维护重复的版本清单。简单的导表或协议生成调用流程使用 `tools/scripts/`，不为单次命令额外创建工具项目。

脚本继续使用 BAT 入口和 PowerShell 7 实现。服务器控制台作为独立工具，其具体操作范围和部署方式后续确定。

编译中间文件、可执行文件、发布包和测试报告统一规划到 `build/`；运行日志统一规划到 `logs/`。客户端日志目录用于采集或导出的日志，并不表示浏览器会直接写入该目录。

## Git 忽略约定

`.gitignore` 已包含以下规则：

```gitignore
/code/**/generated/
/logs/
/build/
```

生成代码、运行日志和构建产物不提交到仓库。`code/client/data/`、`code/server/data/`、`code/shared/data/` 中的导出数据需要提交；修改策划源文件并影响导出数据时，更新对应产物并一并提交。`tools/` 中项目所需的第三方工具也需提交，crane 可执行文件不再忽略；`tools/protobuf/bin/` 已从通用 `bin/` 忽略规则中放行。新增第三方工具时确认完整运行文件未被忽略。

可维护的空目录使用 `.gitkeep` 保留。`generated/`、`build/`、`logs/` 已在本机创建，但不放置跟踪文件；新的克隆中由生成、构建或运行流程按需创建。

## 新拉库后的目标流程

在 .NET SDK、PowerShell 7 和运行所需的服务连接配置准备好后，流程为：

1. Proto 导出，生成未入库的协议代码。
2. 表格导出，生成未入库的 C# 配置代码，并按需要更新已入库的数据。
3. 代码编译，依赖还原由构建入口处理，输出到 `build/` 后运行。

自研导出工具如果需要先编译，由对应工具入口自动处理；导出工具不能依赖尚待自己生成的游戏代码。其他玩法编辑器已经导出的数据随仓库提供，没有修改其源文件时不要求重新运行编辑器。

Ping/Pong 联通工程已在构建时从 `code/shared/protocols/` 生成协议代码到 `code/server/generated/`，编译产物写入 `build/`。[运行说明](../README.md#pingpong-联通验证)包含八进程联通验收入口。表格导出及完整游戏业务的构建流程仍待接入。
