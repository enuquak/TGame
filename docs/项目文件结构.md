确认日期：2026-11-05。

目录骨架已于 2026-11-05 创建，现有脚本、协作规范和仓库内的 crane 工具已迁移，Git 忽略规则已应用；尚未创建游戏源码工程或安装新的工具。后续细微调整默认只向用户展示 diff；用户要求完整结构时再展示全貌。

## 组织原则

- 先采用单 Git 仓库，游戏源码集中到 `code/`，作为 Codex 日常打开的目录。
- 客户端与服务器目录保持对称；两端的运行配置、生成代码和导出数据分别使用 `config/`、`generated/`、`data/`。
- 自研工具、第三方工具和脚本统一放在顶层 `tools/`，按工具名称组织，不再增加 `third-party/` 分类层。
- 策划维护的原始文件统一放在顶层 `design/`；大型资源、工具实体、框架源码和 SDK 不纳入游戏源码的日常工作范围。
- 开发工具、维护策划文件或排查生成问题时，按任务需要访问相应目录。代码项目、构建配置、依赖声明和测试应保持可用。

## 代码职责与依赖边界

`client/app/` 是客户端应用入口，当前采用 Blazor WebAssembly。未来客户端引擎可能更换为 Godot、Cocos 或其他方案，尚未选定，不提前建立对应适配工程。

`server/app/` 是服务器启动入口，负责读取配置、组装引擎与业务、注册服务和处理退出；它承担之前草案中 `host` 的职责。`server/engine/` 放进程拓扑、连接接入与生命周期、服务发现、日志及 SinglePoint 基础能力，可引用共享协议和基础类型，不依赖宿主或具体业务实现。`server/model/` 放常驻业务数据结构，`server/logic/` 放可选的业务 SinglePoint 子类、业务消息处理和存储逻辑。

进程按类型承载 Entity。`engine/ServerSinglePoint.cs` 是 SinglePoint 基类，也是无业务实现时的默认类。业务需要额外初始化时，在 `logic/entities/` 中提供子类，并使用 `SinglePointFor` 标注声明唯一的角色映射；目前仅 DBMgr、Profile 和 GM 有业务子类。宿主将业务程序集的类型集合交给引擎 `SinglePointRegistry` 校验，业务类缺席是合法情况，非法类型、缺失标注和重复映射仍报错。

启动分为两个阶段：先完成引擎监听、ZooKeeper 注册和首次拓扑连接；再创建对应 SinglePoint，执行初始化并记录完成事件。`ServerNode` 提前创建 `engine/SinglePointState.cs` 中的身份并登记 EntityId，随后 SinglePoint 复用同一个 State，不依赖业务初始化完成握手。没有业务子类时，默认类的角色初始化为空操作；业务构造或初始化失败不会退回默认类。`ServerNode.Ready` 同时检查业务初始化成功与当前连接齐备，节点退出时释放 SinglePoint 持有的资源。联通工程目前将 model 和 logic 源码一起编译。

划分其他 Entity 时，model 保存业务逻辑更新后仍需保留的内存状态。例如 Body 的公会 ID、Soul 的当前生命值属于 model，修改公会归属、计算伤害的方法属于 logic。是否写入 MongoDB 由各字段的存盘需求决定。

`shared/` 放两端实际需要共享的协议、代码和数据。当前两端可引用同一个共享 C# 项目，不复制维护。共享代码不依赖客户端引擎专用 API 或服务端存储实现。未来客户端更换语言时，以协议源定义为基础生成对应代码，不预设 C# 源码仍能直接复用。

引擎使用独立项目 `server/engine/TGame.Server.Engine.csproj`，只引用 `shared/TGame.Shared.csproj` 及所需第三方包。宿主 `TGame.Server.csproj` 引用引擎，继续将 model 和 logic 源码编译到宿主程序集；业务热重载加载边界尚未实现。编译依赖方向为 `app（含 logic、model）→ engine → shared`。

`shared/csharp/` 中的 `ProcessType`、`ServerLogProtocol`、`ServerEnvironment` 和 `ServerRunFiles` 是进程角色、日志协议、环境变量及运行标记的统一声明。服务端和探测客户端引用 `shared/TGame.Shared.csproj`；服务器控制台继续通过项目源文件引用复用这些定义，PowerShell 验收脚本通过 `Import-ServerTypes.ps1` 加载同一份类型定义。日志事件、字段和运行标记值保持兼容。

`tests/probe-client/` 是自动化联通验收客户端，不是 `client/app/` 的游戏客户端。它只引用共享工程，读取验收用例、连接 Gate 并校验回包。服务端工程为 `server/app/TGame.Server.csproj`，入口只处理角色启动，验收脚本分别构建并启动两边。`shared/transport/`、`shared/diagnostics/` 和 `shared/logging/` 分别保存 WebSocket 读帧、Profile 探针数据和 JSON 日志序列化；文件日志落盘继续由服务端负责，探测客户端输出到 stdout。

引擎 `LinkService` 接入 gRPC 连接，`ServerNode` 管理连接、握手、实体归属与连接就绪，`PeerLink` 负责发送及请求等待，`ServiceRegistry` 负责服务发现，`Topology` 定义进程之间的连接关系。服务发现地址由宿主读取现有配置后传入，引擎不读取业务 `TestStorage`。

业务 `logic/node/GameServerNode.cs` 继承引擎 `ServerNode`；SinglePoint 的创建与初始化由引擎基类提供，宿主在引擎初始化完成后调用。`GameServerNode.Messages.cs` 分发消息，`GameServerNode.Profile.cs` 处理 Profile 业务路由。`logic/diagnostics/` 存放 Ping/Pong 及其测试驱动和 GM HTTP 处理；GM HTTP 按进程角色挂载入口，在请求到达时读取延后创建的业务实例。`PeerLink.Profile.cs` 与 `PeerLink.Probes.cs` 通过业务扩展方法包装通用连接，无需向引擎加入业务 partial 类。

`transport.proto` 定义连接服务与帧，继续引用当前支持的诊断及 Profile 消息；`pingpong.proto` 只定义诊断消息。当前引擎仍通过共享程序集使用这一固定消息集合，没有改动消息格式或增加动态协议加载、插件系统。

引擎正常启动时只登记本进程的 EntityId；`Topology` 不维护测试实体映射。Router 按握手携带的实际 GUID 建立实体归属，Profile 服务按进程角色寻址。诊断用例由 `tools/scripts/powershell/Test-PingPong.ps1` 读取本轮启动日志中的 EntityId 后生成，不向正式初始化注入测试 ID。

## 配置与生成流程

| 内容 | 维护位置 | 使用或生成位置 |
| --- | --- | --- |
| 客户端运行配置 | `code/client/config/` | 由客户端按需加载或打包，只含可公开的数据 |
| 服务器运行配置 | `code/server/config/` | 按开发、测试、生产环境维护 YAML |
| 策划 Excel 原表 | `design/tables/` | 导表工具按使用范围生成到 `code/client/generated/`、`code/server/generated/` 或 `code/shared/generated/` |
| 行为树、技能等编辑器源文件 | `design/editors/` | 按编辑器原生导出格式，输出到对应端或共享目录下的 `data/` |
| 协议源定义 | `code/shared/protocols/` | 协议工具生成到对应使用方的 `generated/` |
| 手写运营开关与参数 | `code/server/logic/` 中的配置代码 | 延续集中维护 C# 配置的约定，运行中需调整的值不使用 `const` |
| 工具配置、导出规则和模板 | 对应 `tools/<工具名>/` | 随工具维护，不设公共 `config/tools/` |

`generated/` 专门存放自动生成的代码，包括协议消息类和表格导出的 C# 配置代码；`data/` 存放程序读取的导出数据文件。修改源定义后重新生成，不手工维护生成代码。每类配置和协议应明确使用方，只有双端需要的内容进入 `shared/`。

## 工具与运行产物

每个自研工具在自己的目录内维护源码、测试和必要配置；第三方工具同样按名称放入 `tools/`，将项目所需的可执行程序、配套依赖和上游说明、许可证一并纳入版本管理。仓库提交固定实际工具版本，不另维护重复的版本清单。简单的导表或协议生成调用流程使用 `tools/scripts/`，不为单次命令额外创建工具项目。

脚本使用 BAT 入口和 PowerShell 7 实现。Windows 服务器控制台位于 `tools/server-console/`，由 `tools/scripts/Start-ServerConsole.bat` 打开，管理本机开发进程并查看各实例的日志。控制台和联通验收脚本共用 `code/server/config/processes.json` 中的启动列表。

编译中间文件、可执行文件、发布包和测试报告统一规划到 `build/`；运行日志统一规划到 `logs/`。客户端日志目录用于采集或导出的日志，并不表示浏览器会直接写入该目录。

服务进程的日志按类型放在 `logs/server/<进程类型>Server/`。同类实例按 PID 和进程启动 UTC ticks 分文件，每小时滚动，同一小时约满 10 MiB 再分片。Ping/Pong 验收清单、客户端探针输出及核对结果放在 `logs/tools/pingpong/<UTC时间目录>/`。控制台与验收目录仅保存本地运行材料，不参与 ZooKeeper 服务身份；注册路径固定为 `/tgame/test/server-<角色>`，重复注册直接起服失败。

## Git 忽略约定

`.gitignore` 已包含以下规则：

```gitignore
/code/**/generated/
/logs/
/build/
```

生成代码、运行日志和构建产物不提交到仓库。`code/client/data/`、`code/server/data/`、`code/shared/data/` 中的导出数据需要提交；修改策划源文件并影响导出数据时，更新对应产物并一并提交。`tools/` 中项目所需的第三方工具也需提交，crane 可执行文件不再忽略；`tools/protobuf/bin/` 已从通用 `bin/` 忽略规则中放行。新增第三方工具时确认完整运行文件未被忽略。

可维护的空目录使用 `.gitkeep` 保留。`generated/`、`build/`、`logs/` 已在本机创建，但不放置跟踪文件；新的克隆中由生成、构建或运行流程按需创建。

## 新拉库后的目标流程

在 .NET SDK、PowerShell 7 和运行所需的服务连接配置准备好后，流程为：

1. Proto 导出，生成未入库的协议代码。
2. 表格导出，生成未入库的 C# 配置代码，并按需要更新已入库的数据。
3. 代码编译，依赖还原由构建入口处理，输出到 `build/` 后运行。

自研导出工具如果需要先编译，由对应工具入口自动处理；导出工具不能依赖尚待自己生成的游戏代码。其他玩法编辑器已经导出的数据随仓库提供，没有修改其源文件时不要求重新运行编辑器。

共享工程在构建时从 `code/shared/protocols/` 生成协议代码到 `code/shared/generated/protocols/`，服务端和探测客户端引用同一份编译结果。控制台的协议导出命令也面向共享工程。编译产物写入 `build/`。[运行说明](../README.md#pingpong-联通验证)包含八进程联通验收入口。表格导出及完整游戏业务的构建流程仍待接入。
