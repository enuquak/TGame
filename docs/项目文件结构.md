# 项目文件结构

目录确认日期：2026-11-05；启动连接门槛与统一配置更新：2026-11-19。

目录骨架已于 2026-11-05 创建，现已包含独立服务器引擎、宿主、业务共享协议和开发控制台。后续细微调整默认只向用户展示 diff；用户要求完整结构时再展示全貌。

## 组织原则

- 先采用单 Git 仓库，游戏源码集中到 `code/`，作为 Codex 日常打开的目录。
- 客户端与服务器目录保持对称；两端的运行配置、生成代码和导出数据分别使用 `config/`、`generated/`、`data/`。
- 自研工具、第三方工具和脚本统一放在顶层 `tools/`，按工具名称组织，不再增加 `third-party/` 分类层。
- 策划维护的原始文件统一放在顶层 `design/`；大型资源、工具实体、框架源码和 SDK 不纳入游戏源码的日常工作范围。
- 开发工具、维护策划文件或排查生成问题时，按任务需要访问相应目录。代码项目、构建配置、依赖声明和测试应保持可用。

## 代码职责与依赖边界

`client/app/` 是客户端应用入口，当前采用 Blazor WebAssembly。未来客户端引擎可能更换为 Godot、Cocos 或其他方案，尚未选定，不提前建立对应适配工程。

`server/app/` 是服务器启动入口，负责日志、配置、引擎组装与退出。`server/engine/` 提供进程配置、拓扑、连接与握手、服务发现、基础 RPC、日志和雪花 ID，不引用业务 Shared、宿主或具体业务实现。当前启动只运行进程基础框架，不创建实体、登记实体归属或执行实体路由。

`server/model/` 用于业务数据结构，`server/logic/` 保留独立存储工具。MongoDB、Redis 和 Profile 存储实现仍在 `logic/storage/`，但服务器启动不初始化 DBMgr/Profile 业务，也不提供实体或 Profile RPC 入口。后续业务生命周期需另行设计，当前没有角色到业务实现的注册表。

启动顺序为日志创建 → 配置加载 → 构建 IoC 根容器 → ZooKeeper 会话与空地址临时占号 → ID 初始化 → 监听与主动依赖连接 → 发布服务地址 → `PROCESS_READY`。实例名通过 `ServerProcess.FormatName` 生成为 `Router1`、`Base1` 等带编号名称。空地址占号不进入服务发现快照，但可作为主动连接的合法身份。

首次启动时，每种主动目标类型的已握手不同实例数达到 `process.yaml` 的 `processes` 对应数量后，`FirstLinks` 完成，`ServerNode.Ready` 为真。`Ready` 从首次完成状态派生，运行期部分或全部依赖断开都不撤销就绪，继续接受入站并持续发现、重连；未连接 RPC 返回 `Unavailable`，断线待处理请求失败。门槛为 `0` 的类型不阻塞首次启动，但仍发现并连接。无主动依赖时可直接就绪，不等待入站连接；主动依赖必须无环。`LinkService` 转交 `AcceptConnectAsync` 检查首次就绪及对端占号身份。

`shared/` 仅放业务层需要共享的协议、代码和数据，不承载引擎公共能力。客户端业务、服务器业务和工具可按需引用同一个业务共享 C# 项目，不复制维护。业务 Shared 不引用服务器引擎、客户端引擎专用 API 或服务端存储实现。未来客户端更换语言时，以业务协议源定义为基础生成对应代码，不预设 C# 源码仍能直接复用。

引擎使用独立项目 `server/engine/TGame.Server.Engine.csproj`，只引用所需第三方包。宿主 `TGame.Server.csproj` 显式引用 Engine 和业务 Shared，继续将 model 和 logic 源码编译到宿主程序集；业务热重载加载边界尚未实现。编译依赖为 `app（含 logic、model）→ engine` 和 `app（含 logic、model）→ shared`，Engine 与业务 Shared 之间没有项目引用。

`engine/configuration/` 中的 `ProcessType`、`ServerGroup`、`ServerConfiguration`、`ServerRunFiles` 和 `EngineEnvironment` 统一声明进程角色、配置解析与配置值、数量计划、类型连接规则、运行标记和引擎环境变量；纯配置 `MongoStorageSettings`、`RedisStorageSettings` 也在此目录，不携带数据库驱动或业务实现。服务器运行时读取 `process.yaml` 的 `connections` 与 `process.yaml` 的 `processes`；后者同时供控制台决定初始启动数量，并由 `ServerGroup.GetStartupMinimum(ProcessType)` 提供首次连接门槛。`shared/csharp/` 保留业务 `ProfileLogEvents` 和存储凭据环境变量 `ServerEnvironment`；`TGAME_SERVER_CONFIG` 由 `EngineEnvironment.Config` 声明。控制台显式引用 Engine 和业务 Shared；PowerShell 的 `Import-ServerTypes.ps1` 从引擎目录加载基础声明，同时加载业务环境变量定义。

`engine/ServerNode.cs` 管理连接、握手、首次数量门槛、启动就绪与请求分发；`ServerNode.Discovery.cs` 按成员快照持续维护所有匹配实例的动态连接，首次达标后仍连接新实例，数量不限制最大连接数或编号。`PeerLink` 按连接创建，负责发送、响应匹配、超时、取消及关闭时结束等待项；注入的 `ServerConfiguration` 提供 `GetDialTargets`、`Dials` 和 `ArePeers` 类型连接查询，注入的 `ServerGroup` 提供首次连接门槛。通过 `ServerNode.CallPeerAsync` 可以直接向已连接的实例发送 RPC；当前没有业务处理入口，收到请求返回 `Unimplemented`，不转发到第三个进程。

`engine/ZooKeeperProxy.cs` 由 App 注册为 IoC 单例，通过实例方法提供进程占号、地址发布和发现、worker 租约操作。构造不连接；客户端、节点读写与监听集中在代理中，内部 `ZooKeeperSession` 管理会话有效性。宿主显式连接并认领身份后，再初始化 `engine/identifiers/IdGenerator.cs` 的共享实例。节点、连接及存储工具通过构造函数或参数接收所需依赖，用法见[雪花 ID](雪花ID.md)。服务发现与 ID 分配共用同一代理和会话；后台工作停止后异步释放容器，ID worker 租约先于 ZK 会话释放。

App 使用单个根容器组装服务，Engine 不依赖容器或服务定位器。App 显式加载一个 `ServerConfiguration`，注册它及其持有的 `Group`、ZooKeeper/ID 选项，不保存全局 `Current` 或静态配置实例；认领完成的 `ServerProcess` 作为不可变身份共享。`GameLog` 在配置加载前由 App 创建并注册为已有共享实例，容器不接管它的释放；App 在启动与清理错误记录后最后释放日志。Gate 使用 HTTP/1.1 监听，其余进程使用 HTTP/2；当前不加载或管理 TLS 证书。

`engine/protocols/transport.proto` 定义连接服务、进程握手与基础 RPC 帧。`Frame` 分为握手、请求和响应；请求包含请求 ID 与 `Any` 负载，响应携带同一请求 ID，并在负载和错误之间二选一。`shared/protocols/profile.proto` 继续定义独立业务摘要消息，两套协议分别由所属项目生成。

`engine/logging/ServerLogProtocol.cs` 定义通用日志事件和字段，`LogEventJson.cs` 负责 JSON 序列化，`ServerLogFiles.cs` 统一文件名生成与解析，`ServerFileSink.cs` 负责按小时和大小分片及追加写入，`GameLog` 负责等级过滤和输出组装。控制台按 `ProcessReady`（`PROCESS_READY`）事件判断进程启动就绪；控制台会话标记由工具自行维护，服务器不读取它。

`tests/engine/` 检查程序集边界、配置、进程就绪、动态连接、基础 RPC、日志、ID 和 ZooKeeper，并保留独立存储检查。实体路由与业务入口检查已移除。完整或外部服务联调的执行范围见[服务器启动与动态发现](服务器组配置.md)，历史结果不自动适用于当前版本。

运行配置由 `ServerConfiguration` 从 `TGAME_SERVER_CONFIG` 指定的总入口及 include 文件加载一次，严格绑定字段并校验核心配置、拓扑、数量和引擎选项，随后连同其持有的类型对象注册为 App 根容器单例。私有 `ConfigurationDocument` 只用于一次性绑定，不保留另一份配置状态。`ops.yaml` 包含第三方组件参数；存储字段在独立存储工具使用时校验，基础框架不建立数据库连接。启动器默认选择源码 `server.yaml`，直接把源配置路径传给子进程，不保存配置快照。

## 配置与生成流程

| 内容 | 维护位置 | 使用或生成位置 |
| --- | --- | --- |
| 客户端运行配置 | `code/client/config/` | 由客户端按需加载或打包，只含可公开的数据 |
| 服务器运行配置 | `code/server/config/` | 按开发、测试、生产环境维护 YAML |
| 策划 Excel 原表 | `design/tables/` | 导表工具按使用范围生成到 `code/client/generated/`、`code/server/generated/` 或 `code/shared/generated/` |
| 行为树、技能等编辑器源文件 | `design/editors/` | 按编辑器原生导出格式，输出到对应端或共享目录下的 `data/` |
| 引擎协议源定义 | `code/server/engine/protocols/` | 引擎项目生成到 `code/server/engine/generated/protocols/` |
| 业务协议源定义 | `code/shared/protocols/` | 业务共享项目生成到 `code/shared/generated/protocols/` |
| 手写运营开关与参数 | `code/server/logic/` 中的配置代码 | 延续集中维护 C# 配置的约定，运行中需调整的值不使用 `const` |
| 工具配置、导出规则和模板 | 对应 `tools/<工具名>/` | 随工具维护，不设公共 `config/tools/` |

`generated/` 专门存放自动生成的代码，包括协议消息类和表格导出的 C# 配置代码；`data/` 存放程序读取的导出数据文件。修改源定义后重新生成，不手工维护生成代码。每类配置和协议应明确使用方；业务共享内容进入 `shared/`，引擎基础能力由引擎维护。

## 工具与运行产物

每个自研工具在自己的目录内维护源码、测试和必要配置；第三方工具同样按名称放入 `tools/`，将项目所需的可执行程序、配套依赖和上游说明、许可证一并纳入版本管理。仓库提交固定实际工具版本，不另维护重复的版本清单。简单的导表或协议生成调用流程使用 `tools/scripts/`，不为单次命令额外创建工具项目。

脚本使用 BAT 入口和 PowerShell 7 实现。`StartAll.bat` 按统一配置的 `processes` 数量启动；`StopAll.bat` 正常停止，`KillAll.bat` 强制结束。共用实现位于 `tools/scripts/powershell/`。`server.yaml` 的 `runDirectory` 配置相对仓库根目录的运行组父目录；脚本创建本轮目录并通过 `EngineEnvironment.RunDirectory` 传给 App，不修改源配置。

Windows 服务器控制台位于 `tools/server-console/`，由 `tools/scripts/Start-ServerConsole.bat` 打开，管理本机开发进程并查看各实例的日志。脚本与控制台各自管理运行组，都使用 `process.yaml` 的 `processes` 决定初始启动数量，服务器同时将它用于首次连接门槛；App 构建输出包含 `config/server.yaml`，启动器直接传递选中的源配置路径，两种用途读取同一配置，详见 [服务器组配置](服务器组配置.md)。

编译中间文件、可执行文件、发布包和测试报告统一规划到 `build/`；运行日志统一规划到 `logs/`。客户端日志目录用于采集或导出的日志，并不表示浏览器会直接写入该目录。

服务进程的日志按实例放在 `logs/server/<实例名>/`。文件名为本机时间 `yyyyMMddHHmm.log`：自然跨小时分钟为 `00`，约满 10 MiB 时使用实际分钟，同分钟重复分片追加递增序号。控制台通过日志行的进程身份与时间筛选当前生命周期。控制台与验收目录仅保存本地运行材料，不参与 ZooKeeper 服务身份；注册路径为配置根路径下的 `server-<实例名>`（本地配置例如 `/tgame/test/server-Router1`），按类型启动时自动抢占空闲编号，重复占用已有实例身份会被拒绝。

## Git 忽略约定

`.gitignore` 已包含以下规则：

```gitignore
/code/**/generated/
/logs/
/build/
```

生成代码、运行日志和构建产物不提交到仓库。`code/client/data/`、`code/server/data/`、`code/shared/data/` 中的导出数据需要提交；修改策划源文件并影响导出数据时，更新对应产物并一并提交。`tools/` 中项目所需的第三方工具也需提交，crane 可执行文件不再忽略；`tools/protobuf/bin/` 已从通用 `bin/` 忽略规则中放行。新增第三方工具时确认完整运行文件未被忽略。

可维护的空目录使用 `.gitkeep` 保留。`generated/`、`build/`、`logs/` 已在本机创建，但不放置跟踪文件；新的克隆中由生成、构建或运行流程按需创建。

## 新拉库后的目标流程

在 .NET SDK、PowerShell 7 和运行所需的服务连接配置准备好后，流程为：

1. Proto 导出，生成未入库的协议代码。
2. 表格导出，生成未入库的 C# 配置代码，并按需要更新已入库的数据。
3. 代码编译，依赖还原由构建入口处理，输出到 `build/` 后运行。

自研导出工具如果需要先编译，由对应工具入口自动处理；导出工具不能依赖尚待自己生成的游戏代码。其他玩法编辑器已经导出的数据随仓库提供，没有修改其源文件时不要求重新运行编辑器。

引擎工程从 `code/server/engine/protocols/` 生成通用通信代码到 `code/server/engine/generated/protocols/`；业务共享工程从 `code/shared/protocols/` 生成业务协议代码到 `code/shared/generated/protocols/`。控制台的协议导出命令依次处理引擎和业务共享工程；服务器编译通过两个显式项目引用生成所需协议。编译产物写入 `build/`。[运行说明](../README.md#服务器运行与验证)包含本地 RPC 检查入口。表格导出及完整游戏业务的构建流程仍待接入。
