确认日期：2026-11-05。

目录骨架已于 2026-11-05 创建，现有脚本、协作规范和仓库内的 crane 工具已迁移，Git 忽略规则已应用；尚未创建游戏源码工程或安装新的工具。后续细微调整默认只向用户展示 diff；用户要求完整结构时再展示全貌。

## 组织原则

- 先采用单 Git 仓库，游戏源码集中到 `code/`，作为 Codex 日常打开的目录。
- 客户端与服务器目录保持对称；两端的运行配置、生成代码和导出数据分别使用 `config/`、`generated/`、`data/`。
- 自研工具、第三方工具和脚本统一放在顶层 `tools/`，按工具名称组织，不再增加 `third-party/` 分类层。
- 策划维护的原始文件统一放在顶层 `design/`；大型资源、工具实体、框架源码和 SDK 不纳入游戏源码的日常工作范围。
- 开发工具、维护策划文件或排查生成问题时，按任务需要访问相应目录。代码项目、构建配置、依赖声明和测试应保持可用。

## 代码职责与依赖边界

`client/app/` 是客户端应用入口，当前采用 Blazor WebAssembly。未来客户端引擎可能更换为 Godot、Cocos 或其他方案，尚未选定，不提前建立对应适配工程。

`server/app/` 是服务器启动入口，负责读取配置、组装引擎与业务、注册服务和处理退出；它承担之前草案中 `host` 的职责。`server/engine/` 放通用通信协议、进程配置、拓扑、连接接入与生命周期、服务发现、日志及 SinglePoint 基础能力，不引用业务 Shared、宿主或具体业务实现。`server/model/` 放常驻业务数据结构，`server/logic/` 放可选的业务 SinglePoint 子类、业务消息处理和存储逻辑。

进程按类型承载 Entity。`engine/ServerSinglePoint.cs` 是 SinglePoint 基类，也是无业务实现时的默认类。业务需要额外初始化时，在 `logic/entities/SinglePoint/` 中直接按类名存放子类文件，例如 `logic/entities/SinglePoint/BaseServerSinglePoint.cs`，不再为各子类单独建立目录。业务子类使用 `SinglePointFor` 标注声明唯一的角色映射；目前仅 DBMgr、Profile 有业务子类，GM 使用引擎默认类。宿主将业务程序集的类型集合交给引擎 `SinglePointRegistry` 校验，业务类缺席是合法情况，非法类型、缺失标注和重复映射仍报错。

启动分为两个阶段：先完成引擎监听、ZooKeeper 注册和首次拓扑连接；再创建对应 SinglePoint，执行初始化并记录完成事件。`ServerNode` 不提前生成实体身份，握手只交换进程名。`engine/ServerSinglePoint.cs` 直接持有 `EntityId` 和本地实体集合，创建实例时生成身份，在业务初始化成功后登记本地实体，再通过 `ServerNode.Entities.cs` 发送独立的实体注册请求，收到确认后才完成初始化。没有业务子类时，默认类的角色初始化为空操作；业务构造或初始化失败不会退回默认类。`ServerNode.Ready` 同时检查业务初始化成功、当前连接齐备与实体注册已确认，节点退出时释放 SinglePoint 持有的资源。联通工程目前将 model 和 logic 源码一起编译。

划分其他 Entity 时，model 保存业务逻辑更新后仍需保留的内存状态。例如 Body 的公会 ID、Soul 的当前生命值属于 model，修改公会归属、计算伤害的方法属于 logic。是否写入 MongoDB 由各字段的存盘需求决定。

`shared/` 仅放业务层需要共享的协议、代码和数据，不承载引擎公共能力。客户端业务、服务器业务和工具可按需引用同一个业务共享 C# 项目，不复制维护。业务 Shared 不引用服务器引擎、客户端引擎专用 API 或服务端存储实现。未来客户端更换语言时，以业务协议源定义为基础生成对应代码，不预设 C# 源码仍能直接复用。

引擎使用独立项目 `server/engine/TGame.Server.Engine.csproj`，只引用所需第三方包。宿主 `TGame.Server.csproj` 显式引用 Engine 和业务 Shared，继续将 model 和 logic 源码编译到宿主程序集；业务热重载加载边界尚未实现。编译依赖为 `app（含 logic、model）→ engine` 和 `app（含 logic、model）→ shared`，Engine 与业务 Shared 之间没有项目引用。

`engine/configuration/` 中的 `ProcessType`、`ServerGroup`、`ServerRunFiles` 和 `EngineEnvironment` 是现有进程角色、实例配置、运行标记和引擎日志目录变量的统一声明；`engine/logging/ServerLogProtocol.cs` 定义通用日志事件与字段。`shared/csharp/` 保留业务 `ProfileLogEvents`、宿主配置和存储环境变量 `ServerEnvironment`。控制台显式引用 Engine 和业务 Shared；PowerShell 的 `Import-ServerTypes.ps1` 从引擎目录加载基础声明，同时加载业务环境变量定义。控制台会话标记由 `ConsoleSession` 自行维护，服务器不读取它；引擎只声明通用运行标记。现有类型命名空间、进程角色、日志值、环境变量值和运行标记值保持兼容。

`tests/singlepoint/` 检查程序集边界、SinglePoint 生命周期、通用 RPC 和 Profile 路由。Probe Ping/Pong 协议、服务端入口及专用客户端已移除。`engine/logging/LogEventJson.cs` 保存通用日志 JSON 序列化，文件日志落盘由引擎 `GameLog` 负责。

引擎 `LinkService` 接入 gRPC 连接，`ServerNode` 管理连接、握手、实体归属与连接就绪，`PeerLink` 负责发送及请求等待，`ServiceRegistry` 负责服务发现，`Topology` 定义进程之间的连接关系。统一 ID 入口位于 `engine/identifiers/IdGenerator.cs`：宿主先调用 `InitializeAsync` 并用 `await using` 管理生命周期，引擎与业务统一调用 `IdGenerator.GenId()`，无需传递生成器实例，用法见[雪花 ID](雪花ID.md)。服务发现与 ID 分配共用宿主 ServerSettings 提供的 ZooKeeper 地址，引擎不读取业务配置。

宿主直接创建引擎 `ServerNode`，在引擎初始化完成后由节点创建 SinglePoint，并通过 `InitializeAsync(this, stop)` 传入所属节点。SinglePoint 从节点读取角色，业务初始化成功后直接调用节点的 `RegisterEntitiesAsync`，等待注册确认后完成初始化。`ServerNode` 统一处理请求入队、响应匹配、实体与 SinglePoint 路由；本地命中后直接调用目标实例的 `HandleRequestAsync`。`ProfileServerSinglePoint` 在业务入口解包查询、校验参数并访问存储。业务 SinglePoint 扫描以 `ProfileServerSinglePoint` 所在程序集为入口，不再注册独立的 Profile 消息处理器。

`engine/protocols/transport.proto` 定义连接服务与通用 RPC 帧，通过 Protobuf `Any` 承载业务消息，不引用 Profile 协议。`shared/protocols/profile.proto` 定义业务摘要消息，两者分别由所属项目生成。

`ServerSinglePoint` 提供统一的 `HandleRequestAsync(EntityRpcContext, Any, CancellationToken)` 虚方法。业务子类按自身支持的协议处理请求；默认实现对未知协议返回 `Unimplemented`。实体注册请求由 `ServerNode` 单独处理，其余请求统一按目标路由；通用信封校验由 `PeerLink.ValidateEnvelope` 提供。

运行环境由宿主 `ServerSettings` 从 `TGAME_SERVER_CONFIG` 指定的 YAML 加载；Profile 存储读取其中的连接和凭据配置，宿主将 ZooKeeper 地址及注册根路径传给引擎。`server.local.yaml` 是本地环境实例，宿主不隐式加载它；控制台为新运行组选择配置并保存快照。DBMgr 保留独立的 `dbmgr-storage.yaml` 和密码变量。

SinglePoint 自身初始化时登记本进程的 EntityId；`Topology` 不维护测试实体映射。Router 根据独立的 `RegisterEntitiesRequest` 建立实体归属和 SinglePoint 类型索引，握手中不携带实体 ID。直接相邻进程也同步 SinglePoint 身份，以支持已有连接上的实体调用。断线后清理登记，重连后等待重新注册确认才恢复就绪。正式初始化不注入测试 ID。

## 配置与生成流程

引擎实体 RPC 入口为 `ServerNode.CallEntityAsync<TReply>` 和 `CallSinglePointAsync<TReply>`。Router 按 SinglePoint 类型随机选择实体后按 ID 投递，Gate 经现有 Login/Base 连接接入，回复沿原路返回。目标节点确认实体属于本地且已就绪后，直接调用 SinglePoint 请求入口。Profile RPC 只提供查询，修改实体数据应向该实体发送 RPC；Router 不解析 Profile 内容，也不执行 Profile 业务权限校验。接口用法见 [引擎实体 RPC 连通性](superpowers/specs/2026-11-17-entity-rpc-design.md)。

| 内容 | 维护位置 | 使用或生成位置 |
| --- | --- | --- |
| 客户端运行配置 | `code/client/config/` | 由客户端按需加载或打包，只含可公开的数据 |
| 服务器运行配置 | `code/server/config/` | 按开发、测试、生产环境维护 YAML |
| 策划 Excel 原表 | `design/tables/` | 导表工具按使用范围生成到 `code/client/generated/`、`code/server/generated/` 或 `code/shared/generated/` |
| 行为树、技能等编辑器源文件 | `design/editors/` | 按编辑器原生导出格式，输出到对应端或共享目录下的 `data/` |
| 引擎协议源定义 | `code/server/engine/protocols/` | 引擎项目生成到 `code/server/engine/generated/protocols/` |
| 业务协议源定义 | `code/shared/protocols/` | 业务共享项目生成到 `code/shared/generated/protocols/` |
| 手写运营开关与参数 | `code/server/logic/` 中的配置代码 | 延续集中维护 C# 配置的约定，运行中需调整的值不使用 `const` |
| 工具配置、导出规则和模板 | 对应 `tools/<工具名>/` | 随工具维护，不设公共 `config/tools/` |

`generated/` 专门存放自动生成的代码，包括协议消息类和表格导出的 C# 配置代码；`data/` 存放程序读取的导出数据文件。修改源定义后重新生成，不手工维护生成代码。每类配置和协议应明确使用方；业务共享内容进入 `shared/`，引擎基础能力由引擎维护。

## 工具与运行产物

每个自研工具在自己的目录内维护源码、测试和必要配置；第三方工具同样按名称放入 `tools/`，将项目所需的可执行程序、配套依赖和上游说明、许可证一并纳入版本管理。仓库提交固定实际工具版本，不另维护重复的版本清单。简单的导表或协议生成调用流程使用 `tools/scripts/`，不为单次命令额外创建工具项目。

脚本使用 BAT 入口和 PowerShell 7 实现。Windows 服务器控制台位于 `tools/server-console/`，由 `tools/scripts/Start-ServerConsole.bat` 打开，管理本机开发进程并查看各实例的日志。控制台与服务器共用 `code/server/config/processes.json` 中的进程数量配置；服务器组在运行目录保留配置快照，详见 [服务器组配置](服务器组配置.md)。

编译中间文件、可执行文件、发布包和测试报告统一规划到 `build/`；运行日志统一规划到 `logs/`。客户端日志目录用于采集或导出的日志，并不表示浏览器会直接写入该目录。

服务进程的日志按实例放在 `logs/server/<实例名>Server/`。同一实例按 PID 和进程启动 UTC ticks 分文件，每小时滚动，同一小时约满 10 MiB 再分片。控制台与验收目录仅保存本地运行材料，不参与 ZooKeeper 服务身份；注册路径为配置根路径下的 `server-<实例名>`（本地配置例如 `/tgame/test/server-Router1`），重复注册直接起服失败。

## Git 忽略约定

`.gitignore` 已包含以下规则：

```gitignore
/code/**/generated/
/logs/
/build/
```

生成代码、运行日志和构建产物不提交到仓库。`code/client/data/`、`code/server/data/`、`code/shared/data/` 中的导出数据需要提交；修改策划源文件并影响导出数据时，更新对应产物并一并提交。`tools/` 中项目所需的第三方工具也需提交，crane 可执行文件不再忽略；`tools/protobuf/bin/` 已从通用 `bin/` 忽略规则中放行。新增第三方工具时确认完整运行文件未被忽略。

可维护的空目录使用 `.gitkeep` 保留。`generated/`、`build/`、`logs/` 已在本机创建，但不放置跟踪文件；新的克隆中由生成、构建或运行流程按需创建。

## 新拉库后的目标流程

在 .NET SDK、PowerShell 7 和运行所需的服务连接配置准备好后，流程为：

1. Proto 导出，生成未入库的协议代码。
2. 表格导出，生成未入库的 C# 配置代码，并按需要更新已入库的数据。
3. 代码编译，依赖还原由构建入口处理，输出到 `build/` 后运行。

自研导出工具如果需要先编译，由对应工具入口自动处理；导出工具不能依赖尚待自己生成的游戏代码。其他玩法编辑器已经导出的数据随仓库提供，没有修改其源文件时不要求重新运行编辑器。

引擎工程从 `code/server/engine/protocols/` 生成通用通信代码到 `code/server/engine/generated/protocols/`；业务共享工程从 `code/shared/protocols/` 生成业务协议代码到 `code/shared/generated/protocols/`。控制台的协议导出命令依次处理引擎和业务共享工程；服务器编译通过两个显式项目引用生成所需协议。编译产物写入 `build/`。[运行说明](../README.md#服务器运行与验证)包含本地 RPC 检查入口。表格导出及完整游戏业务的构建流程仍待接入。
