# 技术方案的选型（草稿）

记录日期：2026-11-03。本文整理当前讨论形成的暂定方案，尚未完成原型验证，不代表最终实现结论。

这个项目主要用于从零搭建游戏服务器。客户端也需要有，但现阶段的目标比较简单：能够登录、发送操作、查看状态和战斗结果，帮助验证服务器业务逻辑。

目前暂定客户端和服务器都使用 C#。业务代码的热更新先考虑 HybridCLR 的基础动态加载能力，再由项目自己维护 LogicRouter，通过常驻转发方法隐藏路由细节。客户端先做一个简易 WebGUI，优先考察 Blazor WebAssembly。

## 先约定热更新的范围

这里讨论的热更新，目标是在服务进程持续运行的情况下，保留玩家连接和已有业务状态，让后续业务调用执行新版本逻辑。

为了控制实现复杂度，先约定几个边界：

- 引擎层与业务层分离，引擎层不做热更新预设。
- 只更新业务函数的实现，数据结构和 RPC 协议不变。
- 按函数签名及共享接口也保持稳定来设计。
- 涉及数据结构、协议和常驻接口变化时，通过其他发布流程处理。
- 更新发生在明确的业务安全点，不要求把一个执行到一半的函数强行切换成新实现。

因此，需要解决的核心问题是：如何加载新版逻辑，以及如何让现有业务调用切换到新版。

## 业务语言暂定为 C#

C# 能提供静态类型检查、IDE 支持以及比较完整的基础库。对于这个项目，另一个实际好处是客户端与服务器可以统一语言，共享协议消息、枚举和适合跨端使用的数据定义，减少重复维护。

不过，使用相同语言不意味着客户端需要引用整个服务器业务程序集。游戏的权威状态和业务判定仍放在服务器，测试客户端通过协议提交操作、展示结果。

热更新也不是解释型语言独有的能力。普通 C# 构建通常先生成包含 IL 和元数据的程序集；采用 JIT 的 .NET 运行时，可以在执行期间将 IL 编译成机器码。解释器则可以读取中间指令并执行其含义。这些执行机制，都需要另外配合版本加载、入口切换和状态管理，才能形成完整的 reload 流程。

## 热更新：基础动态加载，加上自己的 LogicRouter

HybridCLR 的核心是 AOT + Interpreter：它扩展 Unity 的 IL2CPP 运行时，使动态加载的 C# 程序集能够通过解释器执行，并与提前编译的代码协同工作。

社区版提供基础动态加载能力，例如通过 `Assembly.Load(byte[])` 加载业务 DLL，再调用其中的类型和方法。但加载新代码本身不会自动修复旧对象的方法，也不会自动切换已有的委托和业务入口。

HybridCLR 另有商业化的 Hotfix 动态热修复和程序集热重载能力。当前暂定不依赖这两项能力，而是自行实现业务分发和切换。

可以把职责划分为：

| 部分 | 职责 | 是否参与本轮热更新 |
| --- | --- | --- |
| 引擎层 | 网络连接、调度、消息分发、业务模块加载与切换 | 否 |
| 常驻业务类型与契约 | Player 等状态类型、RPC 消息、业务接口、转发方法 | 否 |
| LogicRouter | 持有当前逻辑版本，提供稳定的业务访问入口 | 否 |
| 可替换业务实现 | 技能、任务、背包操作等函数的具体逻辑 | 是 |

业务数据类型依然属于业务层，只是在程序集组织上常驻，不必把游戏业务定义放进引擎。

### 保留自然的业务调用方式

不希望开发者到处手写 `LogicRouter.Current.CalculateDamage(player)`。可以让 `Player` 的成员方法作为固定的转发入口：

```csharp
// 常驻程序集：状态、接口和转发入口
public sealed class Player
{
    public int Attack { get; set; }

    public int CalculateDamage()
        => LogicRouter.Current.CalculateDamage(this);
}

public interface IPlayerLogic
{
    int CalculateDamage(Player player);
}

// 可替换业务程序集：真正参与热更新的实现
public sealed class PlayerLogic : IPlayerLogic
{
    public int CalculateDamage(Player player)
        => player.Attack * 2 + 10;
}
```

业务调用方仍然写：

```csharp
int damage = player.CalculateDamage();
```

更新时，先加载新版业务模块并创建逻辑实例，再让 LogicRouter 指向新实例。`player` 仍然是原来的状态对象，下一次通过转发入口调用时，执行新版业务逻辑。

这是一种通过调用转发实现的逻辑替换，不需要修改 `Player.CalculateDamage()` 自身的运行时代码。方法数量增多后，可以考虑通过 Source Generator 根据约定生成转发方法和接口，减少样板代码。生成器负责新增代码，不直接改写已经存在的方法体。

LogicRouter 需要通过接口访问实现，不在每次业务调用时进行反射查找。反射可以集中用于模块加载、入口发现和实例创建。

### 切换流程与版本一致性

暂定流程是：

1. 加载新版业务程序集，校验依赖、接口与版本信息。
2. 创建并初始化新版逻辑实例，验证通过后再准备切换。
3. 在消息或帧边界暂停目标模块接收新业务处理，等待已有处理完成。
4. 切换当前逻辑版本，再恢复消息处理。
5. 处理旧版本的回调、后台任务、引用和生命周期。

原子替换一个路由引用，只能保证单次读取拿到一个完整的引用，不能保证一整条业务流程都使用同一版逻辑。例如一次攻击包含伤害计算和扣血，如果两个步骤之间发生切换，就可能混用不同版本。

初期优先考虑在没有进行中业务操作时切换。后续如果需要新旧版本并行过渡，再设计按消息固定版本的调用上下文，让整个调用链以及跨 `await` 的操作使用同一份逻辑快照。多模块更新也需要明确哪些模块必须作为同一个版本一起切换。

定时器和事件应尽量调用常驻入口，避免长期保存某一版业务实现的委托。新版实现所需的持久状态也应由常驻对象持有，避免隐藏在会被替换的实例字段或静态变量中。

## 这套选择仍有几个必须验证的点

**首先是服务端运行时。** HybridCLR 主要面向 Unity IL2CPP，它不是给普通 .NET／CoreCLR 服务器安装一个 NuGet 包就能获得的能力。当前只暂定考察 HybridCLR，尚未决定服务器采用什么宿主，也不能据此认定服务器一定使用 Unity。

原型需要先验证：服务端如何承载和部署 HybridCLR 所依赖的运行时，能否满足调试、库兼容性和部署要求。如果最终服务器使用标准 .NET／CoreCLR，则需要重新评估这一层；.NET 自带的动态程序集加载与可回收 AssemblyLoadContext 可以作为对照方案，但不在本文中擅自替换当前暂定选型。

**其次是连续加载多个业务版本。** 社区版的基础加载不能被当作“反复加载同名 DLL，就会覆盖已加载程序集”。自行维护 LogicRouter，只解决入口选择，并不会额外赋予运行时程序集覆盖或卸载能力。

需要验证新版模块采用独立程序集身份后的加载行为、依赖绑定和反射查找规则。仅修改 DLL 文件名不等于修改程序集身份；Player、业务接口等共享类型必须始终来自同一份常驻程序集。

**最后是旧版本的内存。** HybridCLR 社区版不提供程序集卸载能力。清理业务对象引用，不等于程序集及其运行时元数据也会释放。如果采用持续加载新模块的方式，旧版本占用可能累积。需要测试多轮更新后的内存变化，并确定可接受的更新频率和进程维护策略。

这些属于暂定方案的验证条件，不能仅凭一次加载成功，就认为已经解决长期运行服务器的热更新问题。

## 客户端：C# 编写的简易 WebGUI

客户端暂定使用 C#，界面先采用简易 WebGUI，优先验证 Blazor WebAssembly。

Blazor 可以用 C# 编写交互和网络逻辑，通过 Razor、HTML 和 CSS 描述界面。WebAssembly 模式下，客户端 C# 代码在浏览器中的 .NET 运行时执行，适合独立连接游戏服务器。

相比把交互逻辑放在 Web 服务端的 Blazor Server，浏览器内运行的客户端更贴近这里的验证目标：从客户端发出请求，经过网络和协议处理，再接收服务器结果。

初期界面可以围绕以下内容展开：

- 连接服务器、登录与选择角色。
- 查看玩家属性、背包、任务和房间状态。
- 发送移动、攻击、技能等测试操作。
- 查看服务器推送、战斗日志和请求结果。
- 必要时增加简单网格地图，观察位置和状态变化。

暂定项目组织如下，实际命名可在实现时调整：

```text
TGame.Contracts       客户端与服务端共享的消息、DTO、枚举
TGame.Client.Core     客户端连接、协议收发和状态管理
TGame.WebClient       Blazor WebGUI
TGame.Server          服务端引擎和宿主
TGame.Business        常驻业务状态、接口、转发入口和 LogicRouter
TGame.Logic           可替换的业务函数实现
```

浏览器客户端通过实际网络接口提交操作，界面展示服务器返回的结果。协议不变时，可以持续使用相同的测试客户端，验证服务器热更前后的业务行为。

通信层还没有最终确定。普通浏览器页面适合使用 HTTP、WebSocket 等浏览器支持的协议，不能直接使用任意原生 TCP／UDP Socket。如果服务器最终采用自定义 TCP 或 UDP/KCP，需要额外提供浏览器接入层；这种客户端能验证业务流程，但不能完整代表原始传输协议的网络表现。

## 第一阶段原型要回答的问题

- HybridCLR 能否以合适的宿主方式用于本项目的服务器？
- 能否在同一进程内加载 V1、V2、V3，并保持共享类型身份一致？
- 同一个 Player 对象能否通过原有成员方法，在切换后执行新版实现？
- 定时器、事件、嵌套业务调用和异步操作，能否遵守版本切换边界？
- 多次更新后，旧版本内存的增长是否可接受？
- WebGUI 能否通过真实协议验证登录、一次业务操作以及热更前后的结果变化？

先让这些问题在小原型中得到验证，再确定是否把这套组合扩展成完整的开发框架。
