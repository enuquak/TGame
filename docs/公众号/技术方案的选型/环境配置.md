## 1. 部署分工

| 位置 | 安装或运行的内容 |
| --- | --- |
| Windows 本机 | VS Code、.NET 10 SDK、Git、PowerShell 7、OpenSSH 客户端、数据库 GUI、behaviac 设计器、AI 开发工具 |
| Windows 项目目录 | 游戏服务器源码、Blazor WebAssembly 客户端、共享协议、业务 DLL、测试工程、NuGet 依赖、项目级工具 |

| 云端 Docker 容器 | MongoDB、Redis、ZooKeeper、公共游戏服务、ZooNavigator、Portainer、Prometheus、Grafana |
| AI 知识服务 | OpenViking 在 Windows 本机运行，监听 `127.0.0.1:1933`；不占用云端资源、不经过隧道 |
| GitHub | 代码仓库、Actions 工作流、CI 测试结果与覆盖率报告 |

日常游戏服直接在 Windows 上运行，连接云端数据库。云端公共服通过 Docker 网络访问同机组件。

本机基础方案不要求 Docker Desktop、WSL、Unity，也不需要安装 MongoDB、Redis、ZooKeeper 服务端。ZooKeeper 所需 Java 放在其容器中；普通 Blazor WebAssembly 开发先不安装 AOT 所需的额外工作负载。


```powershell

```

## 3. Windows 本机的 AI 开发环境

### 3.1 Agent 客户端与 Superpowers

本配置以当前使用的 Codex 为接入示例。准备 Codex 桌面客户端或官方 VS Code 扩展并完成登录；VS Code 扩展 ID 为 `openai.chatgpt`。使用哪一种客户端，不影响游戏服务器的语言与部署方式。[OpenAI 官方 IDE 说明](https://learn.chatgpt.com/docs/codex/ide)

Superpowers 是安装到 Agent 的技能/插件，不是游戏服务器依赖。当前上游说明提供 Codex 插件目录安装方式：在 Codex 插件页面搜索 Superpowers 并安装。若同时使用其他 Agent，需要按该 Agent 的集成方式单独配置。[Superpowers 安装说明](https://github.com/obra/superpowers#installation)

验收：新会话能看到已启用的 Superpowers，并能读取 TGame 工作目录。

### 3.2 Serena + Roslyn

Serena 放在 Windows 本机，分析本地源码和工程引用。准备 Git、uv、.NET 10 SDK、PowerShell 7；Python 可以由 uv 管理，无需为游戏服务器额外安装 Python。

当前官方安装方式：

```powershell
uv tool install -p 3.13 serena-agent
serena init
serena --help
```

首次安装完成后，用 `uv tool list` 记录实际安装版本；后续通过固定版本复现。若提示命令找不到，检查 uv 的工具目录是否在 PATH 中，并重开终端和 Agent。

Serena 的 C# 后端使用语言标识 `csharp`，对应 Roslyn Language Server。官方要求 .NET 10+，Windows 还要求 `pwsh`。[Serena 安装说明](https://oraios.github.io/serena/02-usage/010_installation.html)、[C# 语言支持](https://oraios.github.io/serena/01-about/020_programming-languages.html)

在 Codex 的用户级 `~/.codex/config.toml` 中添加以下示例配置。Windows 上 `~` 对应用户目录，当前用户示例是 `C:\Users\Administrator`：

```toml
[mcp_servers.serena]
command = "serena"
args = ["start-mcp-server", "--context", "codex", "--project", "C:/Users/Administrator/Desktop/workspace/TGame"]
startup_timeout_sec = 120
```

工程路径按实际克隆位置修改。若 Agent 找不到 `serena`，通过 `Get-Command serena` 确认可执行文件路径，再把 `command` 改为绝对路径。固定项目路径可避免桌面 Agent 的工作目录与工程目录不一致。MCP 配置方式见 [OpenAI 官方说明](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)及 [Serena 客户端接入](https://oraios.github.io/serena/02-usage/030_clients.html)。

验收：建立实际 C# 工程并恢复依赖后，Serena 能定位类或方法，并找到跨文件引用。仅有 Markdown 文档时，尚不能完成 C# 符号索引验收。

### 3.3 OpenViking 本地接入

本项目开发在 Windows 本机进行，OpenViking 服务和 Codex 适配器均在本机配置。服务地址为 `http://127.0.0.1:1933`，无需 SSH 隧道。日常双击 `tools/scripts/Start-OpenViking.bat`，或从终端运行同一入口。

已安装 OpenViking `0.5.3` 与 `openviking-memory` 插件 `0.11.18`。Embedding 使用本地 CPU 模型 `bge-small-zh-v1.5-f16`（512 维），内容处理通过 `openai-codex` 复用当前 Codex ChatGPT 登录，模型为 `gpt-5.6-terra`。无需另填 Embedding API 密钥；内容处理仍需联网并受对应账号权限和额度约束。

本机配置、数据目录、启停及插件信任步骤见 [OpenViking 本机配置](../../OpenViking本机配置.md)。服务安装、MCP 检索可用与自动会话采集是分别验收的能力；自动 hooks 需要 Codex 加载插件并由用户确认信任。

### 4.1 宿主机基础环境

先检查实际操作系统和架构：

```bash
cat /etc/os-release
uname -m
dpkg --print-architecture
free -h
df -h
```

`x86_64` 对应 Docker 的 `amd64`，`aarch64` 对应 `arm64`。镜像和二进制程序必须提供相应架构。Ubuntu 22.04 在 Docker Engine 官方支持列表中。[Docker Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/)

宿主机准备以下内容：

| 内容 | 用途 |
| --- | --- |
| OpenSSH Server | Windows 远程登录与隧道 |
| 有 sudo 权限的部署账号 | 安装 Docker、维护部署目录 |
| ca-certificates、curl | 获取官方仓库和发行包 |
| Git，可选 | 在云端拉取 Compose 与配置文件；也可以通过发布流程同步 |
| Docker Engine 29.9.3 | 运行服务容器 |
| Docker Compose 插件 5.7.0 | 编排容器、网络、端口和持久化卷 |

新环境可先执行：

```bash
sudo apt-get update
sudo apt-get install -y openssh-server ca-certificates curl git
sudo systemctl enable --now ssh
```

云端以容器运行公共服时，宿主机不用单独安装 .NET SDK、Java 或 Python；对应运行环境由镜像携带。

### 4.2 安装指定版本的 Docker 与 Compose

按 [Docker 官方 Ubuntu 指南](https://docs.docker.com/engine/install/ubuntu/#install-using-the-apt-repository)添加官方 APT 软件源。以下适用于 Ubuntu 22.04：

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: jammy
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt-get update
apt-cache madison docker-ce docker-ce-cli docker-compose-plugin
```

从输出中选出 Engine/CLI **29.9.3** 和 Compose **5.7.0** 对应的完整 APT 版本字符串，再替换以下占位符：

```bash
sudo apt-get install -y \
  docker-ce='<Engine 29.9.3 的完整 APT 版本字符串>' \
  docker-ce-cli='<CLI 29.9.3 的完整 APT 版本字符串>' \
  containerd.io \
  docker-buildx-plugin \
  docker-compose-plugin='<Compose 5.7.0 的完整 APT 版本字符串>'
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version
sudo docker run --rm hello-world
```

不同发行版的 APT 版本字符串有前缀、后缀，不能只把 `29.9.3` 当作完整包版本。如果指定版本未出现在源中，应核对官方发行包和软件源，不自动替换为任意最新版。Buildx 和 containerd 使用软件源提供的兼容版本，并记录实际版本。

后续示例使用 `sudo docker`。若按 Docker 官方方式授予部署用户 Docker 权限，则可以省略 `sudo`。

### 4.4 ZooKeeper 3.8.8 的镜像准备

2026-11-04 核对时，Apache 已发布 3.8.8，但 Docker Hub 官方仓库的 `zookeeper:3.8.8` manifest 查询返回 404。不能直接把该标签写进部署文件并假定可拉取。保留 3.8.8 选型，使用官方二进制发行包自行构建，或在部署时重新检查标签是否已补齐。[Apache 发布入口](https://zookeeper.apache.org/releases/)

自建镜像的准备流程：

1. 下载 `apache-zookeeper-3.8.8-bin.tar.gz` 及对应 SHA-512 校验文件，校验通过后放入镜像构建目录。
2. 选择与云端架构匹配的 Java 运行时基础镜像；例如采用包含 Java 17 的基础镜像，并在构建验收中确认运行兼容性。
3. 解压发行包，提供 `zoo.cfg`，以 `bin/zkServer.sh start-foreground` 作为前台启动命令。
4. 为数据目录配置持久化卷，确保运行用户可写。
5. 将构建产物标记为项目镜像，例如 `tgame/zookeeper:3.8.8`；这只是拟使用的本地镜像名，不是公开可拉取的官方镜像。

单节点开发环境的配置示意如下，目录与最终 Dockerfile 保持一致：

```properties
tickTime=2000
dataDir=/var/lib/zookeeper/data
dataLogDir=/var/lib/zookeeper/log
clientPort=2181
admin.enableServer=false
```

该方案是单节点开发部署，不构成高可用集群。部署后通过客户端执行测试节点的创建、读取、删除，确认持久化目录及权限正确。配置含义参见 [ZooKeeper 管理指南](https://zookeeper.apache.org/doc/r3.8.8/zookeeperAdmin.html)。

### 4.5 Compose、目录与服务配置

云端已使用 `/opt/tgame` 保存部署配置，Compose 中统一维护网络、服务名、端口映射和数据卷。下面保留建议结构；实际配置见仓库 [deploy](../../../deploy/README.md)；OpenViking 使用本机用户目录：

```text
/opt/tgame/
  compose.yaml
  .env
  config/
    redis/
    zookeeper/
    prometheus/
    grafana/
  backups/
```

| 组件 | 首次启动前需要配置的内容 |
| --- | --- |
| MongoDB | 管理员初始化凭据、业务数据库、业务用户、数据卷；区分 `tgame_dev` 与测试数据库 |
| Redis | 用户/密码、数据卷与持久化策略、开发与测试的 key 前缀 |
| ZooKeeper | `zoo.cfg`、数据卷、开发与测试命名空间，例如 `/tgame/dev`、`/tgame/test` |
| ZooNavigator | 与 ZooKeeper 位于可互通的网络，连接容器服务地址 `zookeeper:2181` |
| Portainer | 数据卷、Docker socket、初始管理员账号 |
| Prometheus | `prometheus.yml`、采集目标、数据保留时间与数据卷 |
| Grafana | 管理员账号、Prometheus 数据源、面板与数据卷 |
| 公共服 | 环境名、组件连接地址、服务监听与注册地址、证书、业务 DLL 和配置产物 |

密码和 API 密钥保存在不提交 Git 的实际配置文件或部署密钥中；仓库只保存不含密钥的示例。持久化卷保留容器数据，另外安排备份与恢复验证。

Compose 配置完成后，在云端部署目录执行：

```bash
sudo docker compose config --quiet
sudo docker compose pull --ignore-buildable
sudo docker compose build
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail 100
```

以上命令依赖届时创建的实际 `compose.yaml`；本文没有生成可直接启动全部服务的 Compose 文件。自建 ZooKeeper 服务需要配置 `build`，拉取时跳过该构建项，再由 `build` 步骤生成；其他服务按固定镜像拉取。

### 4.6 公共游戏服与 WebGUI

公共服构建镜像时使用 .NET 10 SDK 构建阶段，运行阶段使用 ASP.NET Core 10 运行时镜像，例如 `mcr.microsoft.com/dotnet/aspnet:10.0`，发布时进一步固定实际补丁版本或 digest。即使主要业务是游戏逻辑，提供 WebSocket/gRPC 的 ASP.NET Core 宿主仍需要 ASP.NET Core 运行时。

业务热重载由常驻引擎中的可回收 `AssemblyLoadContext + LogicRouter` 实现，不是安装到操作系统上的工具。业务 DLL 的发布目录、版本目录、加载权限和回滚方式随工程设计确定。

Blazor WebAssembly 的开发调试在 Windows 完成。需要云端公共验证页面时，将发布后的静态文件交给现有 ASP.NET Core 服务托管即可；若之后选择独立静态站点服务，再补充对应部署。浏览器中的客户端应连接浏览器可访问的地址，而不是 Docker 内部服务名。

## 5. SSH 连接与访问地址

**项目标准（2026-11-05）：本机访问云端数据库、中间件、管理页面及知识服务，统一使用 SSH 隧道，不采用公网 IP 白名单直连。** 云端发布端口和本机转发端口均仅绑定 `127.0.0.1`，云安全组不对公网开放这些服务端口。云端容器内部通信和面向玩家的公共 WSS/HTTPS 入口分别配置。

### 5.1 建立云服务器 SSH 登录

当前 Windows 已通过 `C:\Users\Administrator\.ssh\config` 中的 `TGame-server` 验证密钥登录，使用现有 `id_ed25519`，无需重新生成。日常连接和检查使用项目标准入口：

```powershell
.\tools\scripts\Connect-Server.bat -Check
.\tools\scripts\Connect-Server.bat
```

新开发机若尚无可用密钥，再单独生成并将 `.pub` 公钥通过云厂商控制台或现有登录方式写入云端目标用户的 `~/.ssh/authorized_keys`，配置相同的 `TGame-server` 别名。私钥保留在本机，先核对主机指纹并验证 SSH 登录，再增加端口转发。具体步骤见 [服务器连接说明](../../服务器连接.md)。

### 5.2 云端端口映射

数据库、中间件、管理页面及知识服务的 Docker 发布端口统一绑定到云端宿主机的 `127.0.0.1`。例如 MongoDB 的 Compose 片段：

```yaml
ports:
  - "127.0.0.1:27017:27017"
```

这里仅演示端口格式；完整服务还需要镜像、认证与数据卷。应用在容器内部通常监听容器的可达接口，不能把宿主机端口绑定与容器进程监听地址混为一谈。

下表为项目标准端口映射，由 `tools/scripts/powershell/Start-EnvironmentTunnel.ps1` 维护，BAT 提供启动入口；调整时须同步更新脚本、客户端配置与文档。MongoDB、Redis 使用不同的本地端口以避开 Windows 上已有的服务；OpenViking 直接访问本机 `127.0.0.1:1933`，不在此映射表中。

| 服务 | 容器端口 | 云端发布地址 | Windows 映射地址 |
| --- | --- | --- | --- |
| MongoDB | 27017 | `127.0.0.1:27017` | `127.0.0.1:37017` |
| Redis | 6379 | `127.0.0.1:6379` | `127.0.0.1:16379` |
| ZooKeeper | 2181 | `127.0.0.1:2181` | `127.0.0.1:2181` |
| ZooNavigator | 9000 | `127.0.0.1:9000` | `127.0.0.1:19000` |
| Portainer HTTP（日常） | 9000 | `127.0.0.1:9001` | `127.0.0.1:19001` |
| Portainer HTTPS（保留） | 9443 | `127.0.0.1:9443` | `127.0.0.1:19443` |
| Prometheus | 9090 | `127.0.0.1:9090` | `127.0.0.1:19090` |
| Grafana | 3000 | `127.0.0.1:3000` | `127.0.0.1:13000` |

云端安全组首先保证部署人员能够访问 SSH 端口。公共玩家入口在实际开放时单独配置 WSS/HTTPS；数据库及管理页面按上述隧道方式访问。

### 5.3 Windows 隧道标准入口

基础连接统一复用用户级 SSH 配置中的 `TGame-server`，配置记录见 [服务器连接说明](../../服务器连接.md)。在项目根目录的 PowerShell 7 中统一使用：

```powershell
./tools/scripts/Start-EnvironmentTunnel.bat
./tools/scripts/Start-EnvironmentTunnel.bat -Action Status
./tools/scripts/Start-EnvironmentTunnel.bat -Action Stop
```

脚本后台启动已部署的 7 个服务的转发，启用 `BatchMode=yes`、`StrictHostKeyChecking=yes`、连接超时、转发失败退出及保活检查。隧道需在访问期间保持运行，开机后手动启动；断线后先 Stop 再 Start。OpenViking 使用独立的本机启动入口，不添加云端转发。

不要同时用多个 SSH 进程或 Remote - SSH 转发相同本地端口。日常由项目脚本统一管理转发；排障时若改用其他入口，先停止脚本管理的隧道，并保持同一配置、别名、主机密钥校验和映射地址。远程 VS Code 窗口的终端运行在云端，本地游戏服仍在本地窗口启动。

### 5.4 本地访问与容器内部访问

| 使用方 | 地址配置方式 |
| --- | --- |
| Windows 游戏服、Compass | `127.0.0.1:37017`，另配实际 MongoDB 认证信息 |
| Windows 游戏服、Redis Insight | `127.0.0.1:16379`，另配实际 Redis 用户与密码 |
| Windows 游戏服的 ZooKeeper 客户端 | `127.0.0.1:2181` |
| Windows 浏览器的 ZooNavigator | `http://127.0.0.1:19000` |
| Windows 浏览器的 Portainer | `http://127.0.0.1:19001`，环境 `TGame Docker` |
| Windows 浏览器的 Prometheus | `http://127.0.0.1:19090` |
| Windows 浏览器的 Grafana | `http://127.0.0.1:13000` |
| Windows Agent 的 OpenViking 客户端 | `http://127.0.0.1:1933`，使用本机 `ovcli.conf` 的访问密钥 |
| 云端公共服 | 同一 Docker 网络内使用 `mongo:27017`、`redis:6379`、`zookeeper:2181` |
| Grafana 的 Prometheus 数据源 | 同一 Docker 网络内使用 `http://prometheus:9090` |

Docker 内部服务名以最终 Compose 文件为准。在 Grafana 容器内填 `localhost:9090` 指向的是 Grafana 自己，不能代替 Prometheus 的服务地址。

MongoDB 连接串中的 `authSource` 应填写创建该用户的认证数据库。初始管理员通常在 `admin`，业务用户应按实际创建位置填写；密码中的特殊字符需要正确编码。

SSH 转发 ZooKeeper 的 2181 端口只解决“连接 ZooKeeper”。注册进去的游戏服/gRPC 地址仍须对调用方可达；Windows 无法直接解析 Docker 内部服务名，云端容器也不能直接访问 Windows 的 `127.0.0.1`。本地与云端分别配置监听地址、注册地址和隧道映射。

需要云端主动访问本地服务时，另外设计反向转发。反向端口若只绑定在云端宿主机回环地址，默认桥接网络中的容器不能直接通过自己的 `127.0.0.1` 访问它。

### 6.2 Playwright 浏览器安装

Playwright 的 NuGet 包与浏览器二进制分别安装。先构建测试工程，再执行其输出目录内生成的脚本。以下路径只是工程命名示例：

```powershell
dotnet build .\tests\TGame.WebTests\TGame.WebTests.csproj
pwsh .\tests\TGame.WebTests\bin\Debug\net10.0\playwright.ps1 install chromium
```

按实际工程名、构建配置和目标框架修改路径。初期只安装 Chromium；测试确实涉及 Firefox/WebKit 时再增加。更新 Playwright 包后重新安装匹配的浏览器。[Playwright 浏览器说明](https://playwright.dev/dotnet/docs/browsers)

安装普通 Edge/Chrome 用于人工验证，与安装 Playwright 管理的浏览器不是同一项。云端公共游戏服不需要 Playwright 浏览器；只有实际运行浏览器测试的机器或 CI runner 需要。

### 6.3 Coverlet 与 ReportGenerator

xUnit.net v3 与“测试运行平台”是两个层面，项目建立时还需要固定采用哪条运行路径：

| 测试运行平台 | Coverlet 接入 | 示例命令 |
| --- | --- | --- |
| Microsoft.Testing.Platform（MTP） | `coverlet.MTP` | 配置完成后使用 `dotnet test --coverlet` |
| VSTest | `coverlet.collector`，并配置相应测试适配器 | `dotnet test --collect:"XPlat Code Coverage"` |

同一测试项目按所选平台接入，不把两套驱动同时配置来解决识别问题。VS Code 的测试发现、调试与 CI 命令要一起验证。[Coverlet 官方说明](https://github.com/coverlet-coverage/coverlet)

ReportGenerator 由项目工具清单恢复后，可将 Cobertura 结果转换为 HTML。示例假设覆盖率文件写在 `TestResults`：

```powershell
dotnet tool run reportgenerator -- "-reports:TestResults/**/coverage.cobertura.xml" "-targetdir:build/coverage" "-reporttypes:Html"
```

输出路径应与实际测试命令匹配。参考 [ReportGenerator 官方说明](https://github.com/danielpalme/ReportGenerator)。

测试进程内的覆盖率采集不会自动覆盖另一个独立运行的游戏服进程，也不会自动覆盖浏览器内的 WebAssembly 代码。需要这些覆盖率时，分别配置被测进程的采集方案。

## 7. 监控、AI 服务与 CI 的接通

### 7.1 Prometheus + Grafana

监控平台采用正文确定的 **Prometheus 3.15.1 + Grafana 13.3.0**。

1. 启动 Prometheus，配置持久化卷、采集配置和数据保留策略。
2. 启动 Grafana OSS，在数据源中填写同网络内的 Prometheus 地址。
3. 在游戏服中接入指标出口，记录连接数、请求量、错误量、延迟分布和运行时指标。
4. 需要 Linux 宿主机指标时部署相应采集器，例如 node_exporter；MongoDB、Redis、容器指标也需各自的指标出口或 exporter。安装 Prometheus 本身不会自动获得这些数据。
5. 为压测机器人导出实际请求速率、超时、失败与延迟分布，由同一套 Prometheus/Grafana 采集展示。

指标采集端的具体版本、抓取地址与端口在接入时补齐。Grafana 自带 Prometheus 数据源。[官方数据源说明](https://grafana.com/docs/grafana/latest/datasources/prometheus/)

首阶段可先接通云端服务监控。本地 Windows 游戏服和压测机器人要纳入云端采集时，需要另行配置云端 Prometheus 可达的反向通道；仅建立 Windows 到云端的 `LocalForward` 不会自动提供这条反向路径。

### 7.2 OpenViking 本机配置

服务只监听 `127.0.0.1:1933`，启用 API key 认证。配置与知识数据放在 `%USERPROFILE%\.openviking`，模型缓存位于 `%USERPROFILE%\.cache\openviking\models`。凭据不提交 Git，云服务器不安装 OpenViking。

已完成真实 Codex 模型调用、中文知识导入、CPU Embedding、语义检索、服务重启后读取和 MCP 检索。TGame 工作区启用自动采集/召回，其他工作区默认关闭；已通过原生 `/hooks` 保存信任，并实测自动采集、长期记忆提取和全新 CLI 会话的自动召回。[本机配置与操作说明](../../OpenViking本机配置.md)

### 7.3 GitHub Actions

在仓库的 `.github/workflows/` 下维护工作流，配置代码变更触发和约定的定期测试任务。GitHub 托管 runner 不需要在这台云服务器安装 Agent；将来选择自托管 runner 时才新增对应安装项。

CI 建议按顺序执行：

1. 检出源码，安装与 `global.json` 一致的 .NET SDK。
2. 恢复 NuGet 与项目工具，构建项目。
3. 启动测试依赖并等待就绪，运行单元测试、集成测试。
4. 需要端到端测试时，安装 Playwright 对应浏览器及 Linux 系统依赖，再启动被测服务和客户端。
5. 采集覆盖率，生成并上传报告、测试结果及必要日志。

建议 CI 使用临时测试数据库/容器。若决定连接现有云端组件，runner 也需要单独建立 SSH 隧道，使用独立测试数据库与命名空间，并由 GitHub Secrets 提供连接凭据；它不能继承开发者 Windows 上的隧道。

本文先覆盖构建与测试，自动部署触发条件、镜像仓库、发布账号和回滚流程在发布方案中确定。[GitHub Actions .NET 指南](https://docs.github.com/en/actions/tutorials/build-and-test-code/net)
