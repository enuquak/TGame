
# 服务器语言的选型

之前其实准备了一版编译型语言做引擎层，解释型语言做业务层的设计，比如很常规的cpp+lua，或者网易很爱用的cpp+python

但是近期也确实感觉C#作为业务层的语言的逐渐流行，那引擎层还需要用cpp吗？某fp大佬常说，带了JIT的C#，性能不比cpp差

而且在我日常的开发经验，能不跨语言，真的是一件很幸福的事情，所以最终的话，服务器语言的选型就是全C#了，当然了，引擎层和业务层还是会做区分的

个人认为，在游戏服务器的业务开发，和线上运维中，不重启的热重载是一件很刚需的事情，而且在2026年，如果一个从零搭建一个引擎，还能不考虑这一点，我会怀疑这件事情的必要性。

本来是打算使用 HybridCLR 的 AOT+解释器方案的，但是HybridCLR的热重载是要付费的，没办法直接使用，而且大概率后期正式切换的客户端引擎也不会是C#。所以是打算标准的.Net服务器+DLL热重载设计，牺牲一定程度上的开发时的便利性，不过在主要开发语言是自然语言的现代，似乎这一点也有点无足轻重了

AssemblyLoadContext + LogicRouter，以及“仅更换业务函数逻辑，数据结构和 RPC 协议保持稳定”的边界。

既然是新的引擎，而且是自娱自乐性质的，那就直接使用目前最新的正式版本的 .NET 10 + C#14 了

# 客户端语言的选型

这个项目的客户端，主要是为了做服务器功能的验证

再考虑到我本人比较喜欢前后端是一种语言，可以做一些代码、常量、配置的复用，所以客户端也使用C# 语言

对于一个验证型的客户端来说，WebGUI 无疑是最轻度的，验证最最灵活的方案，但是具体的框架我就不甚了解了，让 codex 推荐了一下，使用 Blazor WebAssembly 框架，语言还是 C# 14

前后端统一语言，后端引擎和业务也统一语言，这就很舒服了

# 通信方案选型

## C2S/S2C通信方案选型

### 传输方案
本来想选 KCP 的，但是由于我们的客户端是WebGUI，浏览器不具备原生收发UDP的能力，考虑到我客户端的定位，我也不想做一些太过重度的事情

而且WebSocket 也具备双向通信的能力，也支持二进制消息格式，所以消息格式的选型也不会有限制

综合下来考虑，暂定这里使用 WebSocket（RFC 6455），线上使用 WSS 加密连接

### 消息格式与序列化

使用 Protobuf 3.36.2

## S2S通信方案选型

gRPC for .NET 2.85.0
