# 序：技术方案的选型

写这套游戏服务器，既是做项目，也是梳理自己对服务器开发的理解。选技术时，我更在意日常写起来是否顺手，出了问题能不能自己查清楚。

下面记录这次选了什么，以及为什么这样选。其中有项目需要，也有个人偏好。

目前已经搭起进程启动、服务发现、基础通信、日志和 ID 等基础框架。客户端、业务热重载和完整游戏业务还在后续计划中。

**语言：服务端统一 C#，运行在 .NET 10 上**

最初考虑过用 C++ 做引擎，Lua 或 Python 做业务。底层控制和脚本开发各有优势，但两种语言之间的调用、调试和对象生命周期，也都得有人维护。

能少处理一层语言边界，对我来说就省心不少，所以最终选了全 C#。引擎和业务照样分层。Go、Java 也能胜任服务端，这次选 C#，主要还是顺手，而且后续客户端也能复用协议和数据定义。

C# 和 C++ 的性能差异要看具体场景，内存分配、GC（垃圾回收）和延迟都得实际测量。当前先把结构和功能做对，遇到热点再优化。

业务热重载计划用 **AssemblyLoadContext + 业务入口切换**：加载新版逻辑，再让后续调用转向新版。初期只替换逻辑，数据结构和协议保持稳定。加载、卸载程序集只是其中一步，旧引用、正在执行的调用和状态保留都还需要单独处理。[.NET 程序集卸载机制](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)

客户端先用于验证服务器，能发操作、看状态就够了，因此计划用 **Blazor WebAssembly**，在浏览器里运行 C#。相比先接入完整游戏引擎，工作范围更小；相比 TypeScript 前端，又能少维护一套语言。代价是浏览器需要下载运行时，功能也受浏览器限制。[Blazor 运行方式](https://learn.microsoft.com/en-us/aspnet/core/blazor/hosting-models?view=aspnetcore-10.0)

仓库里已有的 WPF 程序是服务器控制台，用于在本机起停进程、查看日志。验证客户端还没开始接入。

**通信与第三方：基础能力尽量复用**

| 用途 | 当前选择 | 取舍 |
| --- | --- | --- |
| 宿主与网络监听 | ASP.NET Core、Kestrel、内置依赖注入 | 复用启动、监听和生命周期管理，减少自建基础设施 |
| 进程间通信 | gRPC for .NET + Protobuf | 相比自定义 TCP 协议，省去部分传输与协议工具建设；相比 JSON，消息更紧凑，但不便直接阅读 |
| 日志 | Serilog | 保留结构化事件，方便按进程和请求排查；项目仍需定义事件与输出规则 |
| 配置 | YAML + YamlDotNet | 比 JSON 更方便写注释，但需要严格校验字段、缩进和类型 |

gRPC 支持双向流，让连接两端都能持续发送消息，也能根据协议生成代码。项目用它维护进程连接，至于一条响应对应哪个请求、请求何时超时、如何取消，仍由自己的代码处理。[gRPC 与 HTTP API 对比](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison?view=aspnetcore-10.0)

客户端通信暂定 **WebSocket + Protobuf**，对外用 WSS 加密连接。也考虑过 KCP，但普通浏览器页面不能直接收发原生 UDP 数据。为了一个验证客户端再加适配层，这次先不做。[浏览器网络能力](https://emscripten.org/docs/porting/networking.html)

**存储与协调：MongoDB、Redis、ZooKeeper 各管一件事**

| 组件 | 项目中的用途 | 对比与代价 |
| --- | --- | --- |
| MongoDB | 持久化游戏数据 | 文档结构适合按角色或实体组织数据；若以复杂关联查询、关系约束为主，我会优先考虑 MySQL/PostgreSQL |
| Redis | 缓存可重建的数据 | 相比进程内缓存，便于多进程共享；代价是网络访问，以及失效和一致性处理 |
| ZooKeeper | 实例占号、服务发现、ID worker 租约 | 选择它主要基于已有经验；etcd、Consul 也可作为候选，但切换需要重新验证会话与客户端行为 |

选择 MongoDB，主要看数据会怎样读写。经常一起使用的数据可以放进同一份文档，但文档不能无限增长，索引和跨文档的一致性也得设计。结构灵活，省不掉这些工作。[MongoDB 数据建模](https://www.mongodb.com/docs/manual/data-modeling/embedding/)

ZooKeeper 的临时节点会在会话结束后删除，可以用来记录哪个进程占着哪个编号。不过，网络短暂断开不等于会话已经过期，代码里需要区分这两种情况。[ZooKeeper 会话与临时节点](https://zookeeper.apache.org/doc/r3.8.4/zookeeperProgrammers.html)

三个组件对应的 .NET 客户端是 **MongoDB.Driver、StackExchange.Redis、ZooKeeperNetEx**。目前服务器启动时会使用 ZooKeeper；MongoDB、Redis 的存储代码已保留，但启动时还不会连接数据库或初始化存储业务。

**Agent：工具负责执行，Skill 约束做法**

这个项目也用来摸索怎样和 Agent 一起开发。我用 **Codex** 读写仓库文件、执行命令、查看 diff，自己负责确认需求和关键设计。工具之外，再用 Skill 约定它做事的方法。

| 工具或 Skill | 用途与选择理由 |
| --- | --- |
| Git、PowerShell、rg | 提交与回退、运行脚本、精确文本搜索，是日常工作的基础 |
| Serena + Roslyn | 按符号定位 C# 定义和引用；相较纯文本搜索，更适合追踪代码关系，两者互补 |
| OpenViking | 保存并召回跨会话上下文，减少重复交代；记忆可能过时，仍以当前代码和明确规范为准 |
| Superpowers | 组织需求讨论、计划、调试和验证；相较 OpenSpec，本项目当前更倾向围绕任务推进，避免为小改动维护过多规格材料 |
| Ponytail、ponytail-review | Ponytail 使用 full 控制改动规模，review 检查逻辑、风险与多余代码 |
| C# 专项 Skills | `csharp-expert` 辅助语义与专项选择，`author-component` 用于后续 Blazor 组件；`analyzing-dotnet-performance` 和 `microbenchmarking` 按实际性能问题启用 |

项目规则统一写在 **AGENTS.md 和协作规范**里，Skill 要在这些规则内使用，也不必每次都跑完整套流程。我更关心改动能否看懂、diff 能否查清、验证是否足够，一次生成多少代码倒是其次。

**部署与后续方向**

基础服务用 **Docker Compose** 部署，当前规模先不引入 Kubernetes，本机通过 SSH 隧道访问。日常管理用 Compass、Redis Insight、ZooNavigator 和 Portainer。监控选了 **Prometheus + Grafana**，环境监控已经搭起，游戏服指标还没接入。

测试目前主要靠仓库里的可执行检查程序。后续计划用 **xUnit.net v3** 做单元与集成测试，**Playwright** 验证浏览器操作，**Coverlet + ReportGenerator** 生成覆盖率报告，再通过 **GitHub Actions** 自动运行。这套流程还没有完整接起来。

行为树暂时把 behaviac 留作候选，二维寻路先考虑 A*，等业务需要时再验证。具体依赖版本以仓库配置为准，不要求始终追着最新版走。

全 C# 省去一部分跨语言维护，成熟组件省去一部分基础建设，我就能多花些精力在服务器的运行机制和业务上。当然，接入组件以后也要维护。后续是否保留或替换它们，就看实际开发中是否用得上、代价是否值得。
