# 序：技术方案的选型

从零写一套游戏服务器，第一步总要回答：用什么来写？

我的优先级很简单：自己能理解，日常开发顺手，出了问题能查清楚。这个项目也承担着学习和验证的目的，因此选型会带一点个人偏好，不追求一份适用于所有游戏的标准答案。

截至目前，项目已经有了进程启动、服务发现、基础通信、日志和 ID 等能力。客户端、业务热重载和完整游戏业务仍在后续计划中。

**语言：服务端统一 C#，运行在 .NET 10 上**

最初考虑过 C++ 做引擎、Lua 或 Python 做业务。这种组合能分别发挥底层控制和脚本开发的优势，但也要维护语言绑定、跨语言调试和对象生命周期。

对我而言，少一层语言边界更有价值，所以最终选择全 C#。引擎和业务仍分层，只是不再靠两种语言区分。Go、Java 也能胜任服务端，但当前更看重 C# 的使用习惯，以及后续客户端复用协议和数据定义的便利。

这并不意味着 C# 在所有场景下都和 C++ 一样快。内存分配、GC 和延迟仍需要测量；当前先把结构和功能做对，有热点再优化。

验证客户端计划采用 **Blazor WebAssembly**，在浏览器里运行 C#。相比先接入完整游戏引擎，它更符合现阶段“发操作、看状态”的目标；相比 TypeScript 前端，能少维护一套语言，但要接受运行时下载和浏览器能力的限制。[Blazor 运行方式](https://learn.microsoft.com/en-us/aspnet/core/blazor/hosting-models?view=aspnetcore-10.0)

目前已有的 WPF 工具是本机起停进程、查看日志的服务器控制台，与这个验证客户端用途不同。

**通信与第三方：基础能力尽量复用**

| 用途 | 当前选择 | 取舍 |
| --- | --- | --- |
| 宿主与网络监听 | ASP.NET Core、Kestrel、内置依赖注入 | 复用启动、监听和生命周期管理，减少自建基础设施 |
| 进程间通信 | gRPC for .NET + Protobuf | 相比自定义 TCP 协议，省去部分传输与协议工具建设；相比 JSON，消息更紧凑，但不便直接阅读 |
| 日志 | Serilog | 保留结构化事件，方便按进程和请求排查；项目仍需定义事件与输出规则 |
| 配置 | YAML + YamlDotNet | 比 JSON 更方便写注释，但需要严格校验字段、缩进和类型 |

gRPC 支持双向流和协议代码生成。项目在双向流上维护进程连接，并自行处理请求关联、超时和取消；框架提供传输能力，项目仍要负责通信语义。[gRPC 与 HTTP API 对比](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison?view=aspnetcore-10.0)

客户端通信暂定 **WebSocket + Protobuf**，对外使用 WSS。KCP 也考虑过，但普通浏览器页面不能直接使用原生 UDP Socket，为验证客户端再增加适配层，当前不划算。[浏览器网络能力](https://emscripten.org/docs/porting/networking.html)

**存储与协调：MongoDB、Redis、ZooKeeper 各管一件事**

| 组件 | 项目中的用途 | 对比与代价 |
| --- | --- | --- |
| MongoDB | 持久化游戏数据 | 文档结构适合按角色或实体组织数据；若以复杂关联查询、关系约束为主，我会优先考虑 MySQL/PostgreSQL |
| Redis | 缓存可重建的数据 | 相比进程内缓存，便于多进程共享；代价是网络访问，以及失效和一致性处理 |
| ZooKeeper | 实例占号、服务发现、ID worker 租约 | 选择它主要基于已有经验；etcd、Consul 也可作为候选，但切换需要重新验证会话与客户端行为 |

选择 MongoDB 的依据是预期访问方式。经常一起读写的数据可以内嵌，但文档大小、索引和跨文档一致性仍要设计，不能把“文档灵活”理解成“不需要建模”。[MongoDB 数据建模](https://www.mongodb.com/docs/manual/data-modeling/embedding/)

ZooKeeper 的临时节点随会话结束而删除，适合表达进程占用关系；网络短暂断开与会话过期仍需区分。[ZooKeeper 会话与临时节点](https://zookeeper.apache.org/doc/r3.8.4/zookeeperProgrammers.html)

对应的 .NET 客户端采用 **MongoDB.Driver、StackExchange.Redis、ZooKeeperNetEx**。当前启动链路已使用 ZooKeeper；MongoDB、Redis 的存储代码保留为独立能力，还没有接入服务器启动业务。

**Agent：工具负责执行，Skill 约束做法**

这个项目也在探索如何与 Agent 协作。当前以 **Codex** 为开发入口，让它结合仓库读写文件、执行命令、查看 diff，再由我确认需求和关键设计。

| 工具或 Skill | 用途与选择理由 |
| --- | --- |
| Git、PowerShell、rg | 提交与回退、运行脚本、精确文本搜索，是日常工作的基础 |
| Serena + Roslyn | 按符号定位 C# 定义和引用；相较纯文本搜索，更适合追踪代码关系，两者互补 |
| OpenViking | 保存并召回跨会话上下文，减少重复交代；记忆可能过时，仍以当前代码和明确规范为准 |
| Superpowers | 组织需求讨论、计划、调试和验证；相较 OpenSpec，本项目当前更倾向围绕任务推进，避免为小改动维护过多规格材料 |
| Ponytail、ponytail-review | Ponytail 使用 full 控制改动规模，review 检查逻辑、风险与多余代码 |
| C# 专项 Skills | `csharp-expert` 辅助语义与专项选择，`author-component` 用于后续 Blazor 组件；`analyzing-dotnet-performance` 和 `microbenchmarking` 按实际性能问题启用 |

项目规则统一放在 **AGENTS.md 和协作规范**中。Skill 提供方法，仓库规则决定边界；安装了某个 Skill，也不意味着每次都要运行整套流程。对我来说，能检查的修改、清楚的 diff 和适当的验证，比一次生成多少代码更重要。

**部署与后续方向**

基础服务采用 **Docker Compose**，当前规模下先不引入 Kubernetes；本机通过 SSH 隧道访问。管理工具使用 Compass、Redis Insight、ZooNavigator 和 Portainer。监控选 **Prometheus + Grafana**，现有环境监控已搭起，游戏服指标还需接入。

测试目前以仓库内的可执行检查程序为主。**xUnit.net v3、Playwright、Coverlet + ReportGenerator、GitHub Actions** 是后续测试、覆盖率与 CI 的选型，尚未形成完整流水线。

热重载计划采用标准 .NET 的 **AssemblyLoadContext + 业务入口切换**，先限定为替换逻辑、保持数据与协议稳定。程序集加载和卸载只是基础，旧引用、进行中的调用与状态保留仍需单独解决。[.NET 程序集卸载机制](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)

行为树暂留 behaviac 候选，二维寻路先考虑 A*，等业务需要时再验证接入。具体依赖版本以仓库配置为准，不把“始终追最新版”作为目标。

这套组合的共同取向，是减少跨语言和重复建设，让自己能把精力放在服务器的运行机制与业务上。每增加一个组件，也会增加维护成本；后续是否继续采用，要看它在实际开发中解决了什么问题。
