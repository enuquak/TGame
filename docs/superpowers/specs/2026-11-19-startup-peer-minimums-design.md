# 启动对端数量门槛

用户确认：`processes.json` 的 `Router: 2` 表示依赖 Router 的进程启动时至少连接两个 Router；控制台继续用这份数量创建初始进程。

## 方案

- 复用已有 `ServerGroup` 的只读配置及控制台启动计划，增加按类型读取启动门槛；通过 IoC 注入节点。不另设一套数量配置。
- `connections.json` 仍定义主动连接类型。只统计已完成握手的不同对端实例，入站连接不能替代主动依赖。
- `FirstLinks` 在各主动依赖类型同时达到启动门槛时完成一次。`0` 表示该类型不阻塞启动，仍参与发现和连接。无主动依赖直接完成。
- 启动后不再执行较高数量门槛。保留当前连接健康状态：正门槛类型至少一条连接即健康，全部断开报告连接不全，恢复一条即可恢复；不撤销已经完成的启动阶段。
- ZK Watch、全量匹配实例的连接维护、地址/代次变化和取消清理持续运行，不限制最大连接数或编号。
- App 加载 `processes.json` 并随构建输出分发。控制台保存的启动计划必须同步到本轮可执行快照，避免配置修改后启动数量和运行时门槛不一致。

独立启动数量配置会增加重复维护，用户已选择复用；把数量作为持续运行门槛会违背“只在启动时有作用”，不采用。

## 验证

短范围本地测试覆盖 Router=2 的等待、按类型计数、握手前不计入、达标后的降到1/0/恢复、0门槛、后续新增/替换/退出、IoC和控制台快照。真实ZK/数据库和完整进程组不在本次自动验证范围。
