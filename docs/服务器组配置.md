# 服务器组配置

编辑 `code/server/config/processes.json`，声明本组每种进程类型的总数。例如：

```json
{
  "Router": 2,
  "DBMgr": 1,
  "Scene": 1,
  "Login": 2,
  "Base": 3,
  "Profile": 1,
  "GM": 1,
  "Gate": 1
}
```

必须列出所有进程类型，数量为非负整数。0 表示不启动该类型，整组至少包含一个进程。未知类型、重复键、缺失类型、负数或小数会报错。仓库默认配置保持各类型 1 个。

## 实例名称与启动

所有实例统一追加从 1 开始的编号，即使只配置 1 个也保留编号。上例会启动 `Router1`、`Router2`，`Login1`、`Login2` 和 `Base1`、`Base2`、`Base3`。类型与实例名称分开保存；实例名称用于区分注册地址、连接、控制台页签、日志目录与停止标记。

通过 `tools/scripts/Start-ServerConsole.bat` 打开控制台并启动服务器。控制台将数量配置保存到本次运行目录的 `processes.json`。所有进程读取同一份快照；补起进程、重新打开控制台时继续使用该快照。修改源码配置后，执行“编译并重启”或停止全部进程再“启动服务器”，新组才采用新数量。

旧的无编号运行组不能直接接管为新名称。请先用旧版控制台停止旧组，再启动新组；日志读取工具仍支持历史无编号日志。

手动启动时，先为整组创建一个运行目录并放入配置（目录名称不要求 GUID），再启动其中的实例：

```powershell
$runDirectory = Join-Path $PWD "logs/manual/$([datetime]::UtcNow.ToString('yyyyMMdd-HHmmss-fffffff'))"
New-Item -ItemType Directory -Path $runDirectory
Copy-Item code/server/config/processes.json (Join-Path $runDirectory 'processes.json')

dotnet build code/server/app/TGame.Server.csproj
$env:TGAME_SERVER_CONFIG = (Resolve-Path code/server/config/server.local.yaml).Path
dotnet build/bin/TGame.Server/debug/TGame.Server.dll Login2 $runDirectory
```

以上最后一行只启动 Login2，必须用其他终端或启动器启动同组其余配置实例。未配置的实例名称不能启动。所有启动方式统一等待尚未启动的实例并自动重连，直到拓扑齐备或收到停止请求；ZooKeeper 注册仍有独立超时。控制台会话标记仅供控制台恢复会话，服务器不读取该标记。

## 就绪条件

类型之间的主动连接方向仍由 `Topology.Dials` 定义，每条关系展开为两类所有实例之间的连接。

- 上例中每个 Base 主动连接 `Router1`、`Router2`、`DBMgr1`，并等待 `Gate1` 的入站连接。少任何一个实例都不会标记拓扑就绪。
- 上例中每个 Gate 等待 `Login1`、`Login2`、`Base1`、`Base2`、`Base3` 共 5 条连接。
- 如果 Gate 数量为 2，每个 Login 也必须接收两个 Gate 的连接，并连接配置中的全部 Router。
- 计数以完成 Hello 握手的实例为准。连接重复、实例越界、类型错误或握手失败均不能补足数量。
- 所需实例全部连接后，`FirstLinks` 完成，然后运行角色初始化，最后 `Initialized` 变为 true。
- 无配置邻居时，`FirstLinks` 立即完成。
- 初始化后某个必需实例断线，`Ready` 变为 false；连接重新齐全后恢复。首次连接任务和初始化不会重置或重跑。

配置数量固定了整组成员集合；本功能不在运行中增减成员。0 数量会使该类型不参与连接要求，其对应业务入口可能不可用，应根据部署用途设置。

## ZooKeeper 地址发现

ZooKeeper 地址和节点根路径由 `TGAME_SERVER_CONFIG` 指定的环境配置读取。每个实例启动监听后，将实际地址写入独立临时节点，例如 `/tgame/test/server-Router1` 和 `/tgame/test/server-Router2`。Base 从配置展开预期实例名，分别读取这些节点的地址建立连接；未注册的实例会继续等待。IP 和端口不从实例编号推算，也不写入数量配置。

同组进程必须读取同一轮配置快照。同名节点已存在时立即起服失败，不等待、不覆盖原节点。重连时会重新查询 ZooKeeper，因此补起实例更换端口后仍能连接。当前仍使用本机回环地址；跨机器监听和地址发布不在此次调整范围内。

现有按类型发起的业务调用仍选择该类型的第一个实例；Router 的实体归属与定向转发使用精确实例名称。这里实现的是完整连接与就绪条件，未增加业务负载均衡。

## 日志和验证

服务器环境 YAML 通过 `minimumLogLevel` 控制本次运行的最低日志级别，支持 `DEBUG`、`INFO`、`ERROR`。本地测试配置 `code/server/config/server.local.yaml` 默认使用 `DEBUG`；其他配置省略此项时使用 `INFO`。

```yaml
minimumLogLevel: DEBUG
```

- `DEBUG`：测试排查所需的请求收发、实体路由、服务发现明细和缓存读取细节。
- `INFO`：监听、连接建立、初始化及就绪、存储写入等普通运行记录。
- `ERROR`：进程或初始化失败、RPC 异常、连接丢失、缓存不可用等需要关注和排查的问题。

每条 JSON 日志包含大写 `level` 字段。最低级别为 `INFO` 时不写入 DEBUG；为 `ERROR` 时只写入 ERROR。过滤在序列化及写文件前执行，未打开日志文件时的标准输出也使用相同过滤规则。级别由运行配置决定，与 Debug/Release 编译模式无关。启动配置加载失败仍会记录 ERROR。

控制台会保存环境配置快照；修改级别后需“编译并重启”或停止整组后重新启动才能应用。当前控制台依赖 INFO 日志判断初始化及就绪，因此最低级别设为 `ERROR` 时无法准确展示就绪状态；本次仅调整日志，不拆分状态读取。

例如 Base2 的日志写入 `logs/server/Base2Server/`，记录中 `role` 为 `Base`，`instance` 为 `Base2`。日志文件以 PID 和进程启动 UTC ticks 定位，不再使用 runId。`stop-Base2` 只停止 Base2，`stop` 停止整组。

```powershell
# 只验证日志级别、文件过滤和配置，无需外部服务。
dotnet run --project code/tests/singlepoint/TGame.SinglePointTests.csproj -- --logging

# 在临时副本中验证控制台恢复、单实例停止/补起和整组重启。
pwsh -NoProfile -File tools/scripts/powershell/Test-ServerConsole.ps1 -Configuration code/server/config/processes.json

dotnet run --project code/tests/singlepoint/TGame.SinglePointTests.csproj
```
